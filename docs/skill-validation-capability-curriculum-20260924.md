# 历史驱动的能力课程与单轮 Skill 更新

本次修改不覆盖冻结的历史实验。新增入口是 `skillopt.skill_validation.curriculum_study`。

## 改了什么

1. **历史诊断**：`capability_goals.py` 重放完整开发反馈，读取所有公开检查结果的紧凑摘要和分层详细案例。模型提出能力缺口、竞争解释、应观察的证据和所需任务角色；可以不提出新目标。单次 Current 失败不被标成 Skill 导致的过拟合。
2. **能力任务家族**：`curriculum_tasks.py` 让模型选择受限的操作组合，由宿主生成题面、公开示例和执行器。一组包含“必须保留输入”“必须原地更新”“不限制输入状态”三个契约版本，不是只对原题增加输入。
3. **任务资格检查**：在 Linux Docker 中比较两种参考实现、有限枚举以及错误返回/错误状态控制。失败、不支持、结果缺失均保留；不从失败的生成批次人工补题。这里验证的是任务编译和执行链路，不是 Verifier Gate，也不保证无限输入正确。
4. **学习闭环**：新任务执行 → 实际公开检查 → 同预算一次回答修订 → 全开发反馈 → 至多两条条件规则的新增/替换/删除 → 冻结候选 → 共同确认任务上的配对执行。隐藏审计结果不进入模型反馈。

基础执行器、公开修订、反馈回放和条件规则更新均复用现有模块；没有另写一套 Vxx 框架。

## 对照设计

| 分支 | 课程输入 | Skill 更新 | 共同确认 |
|---|---|---|---|
| No-Skill | 不学习 | 空文本 | 相同任务、相同一次公开修订机会 |
| Generic | 相同受限任务语言，不提供历史目标 | 新任务公开反馈，条件规则更新 | 原始候选强制使用，不根据成败路由 |
| Targeted | 历史记录提出的第一个能力目标 | 同一更新器、同预算、相同初始空 Skill | 同上 |

另外保存“删除历史结果内容”的目标规划消融。它仍使用相同的历史案例契约集合，因此不是完全随机选题的无历史基线，也没有被包装为额外的完整学习分支。

默认预算：每个学习分支 6 个结构家族 × 3 个契约版本 × 2 次执行；共同确认 12 个家族 × 3 个版本 × 2 次执行。确认阶段比较三个条件，共 216 个位置。家族内版本和重复执行**不是新增独立样本**。两个学习分支可有家族交集，必须报告；学习与确认的完全相同结构及固定输入域上行为相同的家族不得跨区。有限行为签名仍不是完整语义独立证明。

先生成两组开发课程，随后生成共同确认课程；只有确认任务生成器能看到开发规格，以便避开重复，不看求解结果。开发任务生成器、求解器和 Skill 更新器都不能提前读取确认任务。所有规格均在第一次学习执行之前冻结。

历史父 Skill 仅用于发现研究假设。本轮两个学习分支均从同一个空结构化 Skill 开始，并重新收集与其版本绑定的证据，不把旧父 Skill 的执行记录冒充新父的证据。冷启动时 No-Skill 与 Current 是同一文本、会共享相同请求回执；它们不构成父 Skill 优劣对照。

## 证据边界与已知限制

- 新任务来源标记为 `synthetic_generated_spec`，不是 HumanEval/MBPP，也不是完整工作簿任务。
- 模型选择任务规格，不能任意输出宿主脚本或标准答案；两种参考实现都在隔离环境执行。
- 主 `requested_behavior` 包含返回值与输入状态的完整契约，公开 wrapper 联合检查。输入保持的辅助 scope 标签并不因此获得独立逐项认证，不得把 wrapper 的空参数当成输入状态证据。
- Research/Rubric 新检查未经独立校准，不进入这轮学习反馈。本轮仅用注册的公开检查做 **shadow 候选实验**，不授予部署或跨域适用权。
- 这次不比较 Research 的独有收益，也没有声称完整协同进化已经完成。
- 目前实现了同机制任务与条件反转；`unconstrained` 只是“不要求保持输入”，不能称为所有无关机制任务。真正的表面迁移、跨域和无关能力任务适配尚未实现。
- 一条学习历史、有限合成空间可能存在高分天花板。应如实报告无提升、无更新或 Pending，不能通过反复换确认题获得正结果。
- 这一步能测试历史是否影响选题，以及反馈是否改变规则。是否提高公开 benchmark 的稳定泛化，仍需冻结后另做独立评测。

## 可运行命令

以下是去除个人机器路径的命令模板；请替换本地历史产物路径和 Linux 源码快照路径。原始运行、协议与下文分数不变。

```bash
python -m skillopt.skill_validation.curriculum_study \
  --repo . \
  --output outputs/skill_validation/curriculum_new_run \
  --historical-parent outputs/skill_validation/natural_20260922_bigmodel_c/parent_skill.json \
  --historical-feedback outputs/skill_validation/development_repair_20260923_a/coverage.json \
  --remote-repo /absolute/linux/source/snapshot \
  --workers 4 --repeats 2 --development-families 6 --confirmation-families 12
```

可加 `--stop-after prepare` 或 `--stop-after learn`。同一输出目录只允许相同代码、配置和冻结输入回放；源码变更后应另用新目录。中断请求保留 intent，不自动重复收费或隐藏重采样。

生成、参考资格检查和待评代码均有回执。Python 生成/学习调度在本机，代码实际执行在 Linux Docker；目前调度仍依赖本机不休眠和 SSH 稳定。

## 本次验收结果

- v1 工程回归：`tests/test_skill_validation_*.py` **1370 passed**。其中新课程/目标/任务模块测试都是显式 fixture，不能代表模型效果。
- GLM-5.3 连通性测试成功；Linux Docker 真实 ping 成功，确认容器已清理。
- 真实试跑 A：4 次模型调用、48,772 个已报告 token、0 API 终止失败。历史规划产生了三个具体假设；但另三个响应带完整 JSON Markdown 围栏，被严格解析器拒绝。因此在生成阶段 **Pending**，没有执行学习任务、没有更新 Skill、没有确认准确率。
- A 的失败属于接口格式兼容性，不是 Research/历史反馈的效果负结论。旧回执、协议和 Pending 原样保留。后继版本仅复用已有 whole-document JSON envelope normalization，不修正文义、不接受混杂说明、不重新解释旧协议成绩。
- A 暴露出另一个实质问题：历史首个目标涉及负数整数幂谓词和浮点开根误差，v1 列表 DSL 无法充分检验。因此 v2 增加受限的完全平方/完全立方谓词与立方变换，用纯整数参考验证；仍不把输入状态反转等同于“允许近似实根”的数学条件反转。
- v2 工程回归：**1439 passed**。3 个手选数值算子组合在真实 Linux Docker 中分别完成 528 次参考/角色比较，均通过正确替代解、状态要求和错误控制检查。这属于工程资格验证，不是三个模型效果实验。
- 真实试跑 B：2 次模型调用、46,391 tokens、0 API 终止失败。盲规划成功；历史规划把 `reason` 放在各 goal 内、缺少规定的顶层字段，被拒绝，停在 **Pending / goals**。它还提出了部分已由固定交付/公开修订流程覆盖的目标。没有学习或确认成绩，不可由此比较两种规划的好坏。
- 后继接口显式提供固定执行流程，只省略重复的宿主 `public_runner.py` 正文，原始完整记录继续在宿主回放；任务、公开示例、结果、全部配对覆盖和待评代码均保留。规划必须寻找基础设施之外的语义能力，不能将 JSON 交付格式包装成新增 Skill。
- 真实试跑 C：两个目标规划均合法；历史分支聚焦精确整数边界，盲规划聚焦尚未观察到的输入保持能力。这仅表明输入信息改变了提出的目标，不证明历史规划更好。目标课程生成了 6 个家族；通用课程请求的 2,048-token 上限全部耗在 reasoning，`finish_reason=length`，无任务正文，因此整个对照停在生成阶段。4 次调用、39,770 tokens；没有 Skill 更新或确认成绩。
- 单独回放 C 的 6 个真实生成规格：**6/6 通过 Linux Docker 任务资格检查**，可编译为 18 个状态契约任务。该回放不补入 C 的失败对照、不恢复训练、不授予验证器或 Skill 权限。记录位于 `outputs/skill_validation/curriculum_c_task_qualification_20260924/summary.json`。
- 最新工程回归：**1443 passed**。协议 D 仅把任务生成上限调为 6,144 tokens；求解器/更新器仍是 2,048。它不是与 C 等计算量的方法消融。两组任务生成仍因 `finish_reason=length` 截断，分别消耗 6,144／6,143 个 reasoning tokens，没有可用任务正文；4 次调用、50,271 tokens，停在生成 Pending。因此不能靠继续放大这个上限宣称接口已稳定。
- A–D 共 **14 次实验模型调用、185,204 个已报告 token**，全部原始回执和失败保留；另有一次独立连通性调用，不计入此成本。四轮均未进行真实 Skill 更新或确认评分。当前没有继续运行的实验进程。汇总见 [结果 JSON](results/skill-validation-capability-curriculum-20260924.json)。

## 两个问题目前解决到什么程度

| 问题 | 已完成 | 仍未证明／未覆盖 |
|---|---|---|
| 先看历史，再决定检测什么 | 完整公开开发回放 → 全量配对摘要＋详细案例 → 带证据引用与竞争解释的能力目标，已真实调用 | 目标的语义准确性、对最终学习的增益；不能把个别回归直接称为过拟合 |
| 围绕能力生成任务家族 | 已由真实模型生成规格，宿主编译完整新任务和三种状态契约，6个家族真实隔离验证通过 | 目前仅有界 Coding 任务；未覆盖完整表面迁移、数学近似条件反转、不相关机制或跨域 |
| 验证反馈用于 Skill 进化 | 单轮课程执行、公开修订、结构化规则更新、共同确认的入口和完整 fixture 回放通过 | 本次真实试跑尚未完成这条学习链的效果比较，不能报告泛化提升 |

核心发现是：**提出一个能力目标，不等于当前任务生成器真的覆盖了这个目标。** 目标→任务能力覆盖、格式/预算可靠性也必须验收，不能看到一个生成任务上的高分就宣布 Skill 泛化成功。

下一步不应继续缩小 batch 或重复放宽上限：先把任务教师改为更可靠的受约束输出（例如从宿主去重的合法操作组合中选择，保留自由目标规划），明确教师阶段的推理预算，再运行已经写好的单轮对照。目标要求但当前适配器未实现的数学条件反转、真正无关任务与跨域检查需单独补齐。所有更新先保持 shadow；不能将“候选回退到 Base”写成学到了泛化能力。
