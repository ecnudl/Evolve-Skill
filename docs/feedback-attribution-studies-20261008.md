# 反馈归因研究（L1 固定Rubric组件实验 / L3 匹配单步反馈实验）——10/8 预注册

状态：**L1 已完成（10/8 09:55–10:54）：登记的主对比为阴性，见 §2.1。L3 经代码审查五轮后通过，10/8 10:58–10/9 06:17 完成：登记的主对比（h2 − 标量）成立，p = 0.047；h2 − 默认不显著（p = 0.46），因此不能归因于 Rubric 演化本身，见 §3.1。** 两者都只用 train/val，不碰 test，不改主表、不替换 S3，也不改任何冻结的学习协议或阶段工具。

## 1. 为什么要做（主表回答不了的两个问题）

主方法 v10 的主表（S3 = 链 h，见[账本](results-and-lessons.md)）里，唯一被接受的更新（QA step 0）用的是默认 Rubric。KOR 阶段 h 的 Rubric 每步都更新了，而且更新有针对性：第2步加入了“只看答案也能核对的约束检查”，专门去抓先前漏掉的错误答案。但现有记录**无法说明演化是否有效**。与 Codex（GPT-6-Astra，ultra）两轮讨论后的诊断：

- **D1 没有反事实测量**：各版本 Rubric 从未在同一批行上比较过；每步的 train 输出都重新采样；校准用的是 proposer 也能看到的同一批行（same-train）。
- **D2 没有 Rubric 选择**：合法的提案就直接成为下一版，没有留出证据证明它更好。
- **D3（经 Codex 更正）**：并非只有被检出的行才带报告。授权步骤里，**所有宿主失败行**都会收到报告（可含 PASS/UNKNOWN 判词）；Rubric 的 `mechanism/applicability/exceptions` 三个字段还会直接进入 analyst 的系统提示。瓶颈在接受环节：严格门控下只有 QA 被接受。另外，未授权步骤的 analyst 既拿不到报告，也拿不到 Rubric 指导。
- **D4**：每条链里每个领域只出现一次，演化后的 Rubric 不会在重访时复用。
- **D5**：唯一被接受的更新用的是默认 Rubric，原因是 v3 的解析失败（v5/v6 已修）。

结论：Rubric 确实变了，也影响了提案的生成，但没有任何匹配的测量能分离出它的作用；而用演化后 Rubric 生成的候选，没有一个通过最终的接受程序。

## 2. L1：固定Rubric组件实验（`fivebench-fixed-rubric-study-v1`，已实现）

- **问题**：在同一批新输出上，h 最终演化出的 Rubric（h2）是否比默认 Rubric 检出更多宿主失败行？
- **语料**：源阶段 h（`/root/fivebench-g-20261006-korbench-chain-rubric_research-h`）的父 Skill（S2）在 90 个 KOR train 任务（30 个规则族 × 3）上做**一次新的 rollout**。用本研究自己的 manifest 和账本，模型、运行环境和恢复策略（v7 交付规则）都与 h 相同。语料是新输出，但任务与演化时用的是同一批，**不构成任务层面的分离**。
- **处理**：4 份冻结的完整 Rubric 记录，必须是同一条演化链，在 prepare 时冻结：
  - default `d4446d9d…`
  - h0 `5bf5f30b…`
  - h1 `8d2ae03f…`
  - h2 `333a229c…`（h 的最终 KOR Rubric）
- **判题**：每个 Rubric × 输出格只判一次；判题提示、解析器和交付处理与 v7 完全相同。执行顺序：先按登记种子把所有格打乱、封存，然后先单独跑第一格作为健康屏障，其余并发。各组的记录目录和账本逻辑 ID 分开。不做 Rubric 提案，不跑 Research、analyst、门控、val 或 test。
- **端点**：分母都是全部合格行（已知宿主分数的行），各组相同。
  - 拒绝：至少一条有效的 FAIL 检查。
  - 检出率：拒绝行 / 全部合格宿主失败行。
  - 误拒率：拒绝行 / 全部合格宿主通过行。
  - 弃权（含终端交付）不算拒绝，单独报告。
  - v7 的条件率和授权情况另列。
- **主对比**：h2 − 默认 的检出率之差，用规则族层面的精确双侧 sign-flip 检验（按族卷积，不抽样）。只有在差值 > 0 且 p ≤ 0.05 时才能下方向性结论。
- **安全条件**：两者都满足才可以写“验证器改进”。
  - 误拒率差的单侧 95% 上界 ≤ 5 个百分点。上界用按族整体重抽样的 bootstrap 计算，20,000 次，种子已登记。
  - h2 的 v7 条件误拒率 ≤ 0.25。

  若不满足，只能写“检出更高，误拒率为 X 对 Y，不确定性为 Z”。
- **次要分析**：逐行精确 McNemar、h0/h1 的描述统计、按族的分表、覆盖率、交付计数。
- **盲审**：h2 与默认在“是否拒绝”上有分歧的所有行，生成盲审包：给出公开题面、截断后的回复，以及拒绝方的 FAIL 检查；不含 Rubric 身份和宿主标签，对照表放在 host_only。之后由独立审稿人判断每条违约声称：
  - 是否有公开合同支持；
  - 不支持；
  - 无法判定。
- **结论边界**：结果为正，只能说“在这些固定 KOR train 任务的新输出上，冻结的最终演化 Rubric 改善了登记的验证器端点”。不能说明以下几点：
  - 演化是单调的；
  - 策略搜索是可靠的；
  - 能泛化到未见过的规则族；
  - Research 有收益；
  - Skill 有改进。
- **中断规则**：中断即 pending，没有结论，不续跑。结果不好也照样报告；不得改选 h0/h1，也不得改判题提示后仍称是同一实验。
- **代码与测试**：
  - 代码：[fixed_rubric.py](../skillopt/feedback_study/fixed_rubric.py)、[common.py](../skillopt/feedback_study/common.py)、[CLI](../scripts/run_fivebench_fixed_rubric_study.py)。新包放在 `continual_learning` 之外，因此 `contracts.sources()` 和所有冻结文件都不变，已与快照 m 做逐字节核对。
  - 测试：[test_feedback_study_fixed_rubric.py](../tests/test_feedback_study_fixed_rubric.py)。
- **预算**：
  - 调用：90 次 solver（另有长度恢复）加 360 次判题（每次判题最多 4 个请求），上限 1,800 个调用、1,440 个验证器请求。
  - token：已报告用量达到 12M 即停止。
  - 运行期间持有 F 的 native 锁。

### 2.1 L1 结果（`/root/fivebench-g-20261008-l1-fixed-rubric-o`，[结果](results/fivebench-fixed-rubric-l1-20261008.json)）

- **数据**：90 个合格行（宿主失败 20、通过 70、0 未知）；360 格全部有判定，0 次终端交付，用量完整。
- **各 Rubric 的检出和误拒**（分母分别为 20 和 70）：
  - 默认：9（45%）/ 9（12.9%）
  - h0：6 / 1
  - h1：3 / 5
  - h2：7 / 7
- **主对比**：h2 − 默认的检出率差 −0.10，6 个有信息的族，p=0.69，**不成立，方向相反**。
- **安全条件**：误拒差 −0.029，单侧 95% 上界 0.062 > 0.05，不满足。
- **逐行 McNemar**：检出 2 对 4，误拒 6 对 8。
- **登记措辞**：`no_supported_detection_difference`。
- **解读**：这次没有证据表明 Rubric 演化提高了检出。演化移动了检出与误拒的取舍（h0 误拒最少）；h1 两项都更差。
- **盲审**（次要、描述性；审稿人只拿到盲审包）：h2 与默认的 20 条分歧行逐条判断有无公开题面支持。
  - 只有 h2 拒绝的 8 行：3 行有支持。落在宿主失败行上的 2 行都有支持；宿主通过行上的 6 行只有 1 行有支持，其余是裁判自己算错。
  - 只有默认拒绝的 12 行：2 行有支持。宿主失败行上的 4 行只有 1 行有支持——默认 Rubric 多出的“检出”大多是在要求写出可见推理步骤，与失败相关，但不是成立的诊断。
  - 结论：h2 检出更少，但检出更常成立。样本只有 20 条，只作描述。[盲审结果](results/fivebench-fixed-rubric-l1-audit-20261008.json)

## 3. L3：匹配单步反馈实验（`fivebench-matched-feedback-study-v1`，已完成，见 §3.1）

- **问题**：同一个父 Skill（S2）、同一批 train 输出，只换反馈，单步提案的效果是否不同？
- **领域**：KOR。QA 留作之后的复制实验；它那次被接受的更新用的是默认 Rubric，回答不了演化 Rubric 的问题。
- **三组**：
  - A：标量反馈。
  - B：A，加上固定默认 Rubric 的授权报告和 Rubric 指导。
  - C：A，加上冻结 h2 的授权报告和 Rubric 指导。用完整的 h2 记录，中途不换成任何 L2 产物。
- **区组**（共 8 个，都从同一个父 Skill 出发，接受的候选不会成为下一区组的父 Skill）：
  1. 每个区组共享一次新的 train rollout，并冻结已知行掩码、标量反馈、顺序和 minibatch 种子。
  2. 用默认 Rubric 和 h2 分别判这批输出，各自按冻结的授权规则校准。授权失败的组去掉报告和 Rubric 指导（输入等同 A），但仍保留独立的那次模型提案抽取，不重试。
  3. 每组各做一次原生的 reflect → merge → rank → apply。
  4. 先冻结所有候选和可受理性判定，再在完整的 250 个 val 位置上评测每个变动过的可受理候选，不做 v9 筛选。
  5. 每个区组还评测一次共同的父 Skill val。无更新或不可受理时回落到父 Skill，并单独记录这一处置。
- **主要端点**：已证实成功的产出，即通过数 / 计划位置数；unknown 单列为一种状态。
- **主对比**：C − A，8 个区组差值的精确双侧 sign-flip 检验，α = 0.05，方向性结论要求效应为正。
- **次要对比**：B − A、C − B。没有可信的 C − B 证据时，不得声称是 Rubric 演化本身改进了提案。
- **随机化**：区组内按执行时段随机分配组别。
- **分析单元与边界**：
  - 不能把行或位置当成独立实验；8 个区组也不等于 8 段独立的演化历史。
  - 结论限于这一个父 Skill、这个模型和这批任务。
- **泄漏防护**：提示字段用白名单，并用哨兵测试检查。v10 现有的抄标签检查登记表是空的，不能当作记忆筛查的证据；如需额外筛查，必须冻结、各组相同，并在 val 之前执行。
- **预算估计**：约 10.5–10.7k 次调用，约 40M 已报告 token（只是规划量级，不是保证）。
- **实现**：[matched_feedback.py](../skillopt/feedback_study/matched_feedback.py)、[CLI](../scripts/run_fivebench_matched_feedback_study.py)（源核验复用 L1 已审的 `spec_from_stage`）、[启动器](../scripts/run_fivebench_matched_feedback_linux.sh)、[测试](../tests/test_feedback_study_matched_feedback.py)。`propose_arm` 与冻结的 `propose_native` 逐步相同，只有两处不同：各组有自己的逻辑 ID，报告和 Rubric 绑定到本组自己的记录树。准备时封存实现身份，运行前在锁内比对，不一致即拒绝。**失败语义**（Codex L3-1 裁定）：任何原生提案失败（analyst JSON 重试后仍拒、回复截断）都使整个研究 pending，不续跑，也不改记为“不可受理”。超预算候选和无更新回落到父 Skill，并记录处置。
- **前置条件**：先检视 L1。L1 没有结论时，L3 仍可回答“h2 反馈是否有帮助”，但不能把“验证器改进”当作已确立。

  | **C − A（主）** | +6、+9、+1、+12、+11、−2、+2、+1 | **+5.0** | **0.047** |
  | B − A | −3、+4、−1、−2、+1、+12、+10、−2 | +2.4 | 0.37 |

- **验证器端**（train，8 个区组合计）：
  - 检出（/204 个宿主失败行）：默认 77（37.7%），h2 76（37.3%）。

- **解读**：
  - h2 验证器反馈产生的单步候选，比只有 pass/fail 的标量反馈平均多通过 5 个 val 位置（+2.0 个百分点）。
  - C − B 不显著。按预注册，**不能声称是 Rubric 演化本身改进了提案**；B 与 C 的差异在噪声内。三组排序（A < B < C）只是方向性观察。

- **限制**：
  - p 只是刚过阈值。8 个区组精确检验的最小 p 是 0.0078，一个区组的符号变化就可能改变结论。
  - 只有一个域（KOR）、一个父 Skill，单步提案，不经门控。
  - 只在 val 上测量，没有测 test，不改主表。
  - 8 个区组用的是同一批 val 位置，不是 8 段独立的演化历史。
- **成本**：

## 4. 推迟的部分（L2：带门控的 Rubric 演化）

L2 暂不做（Codex 的意见：在确认现有演化 Rubric 有用之前，不要把搜索、选择和反馈的改动叠在一起）。将来做时的要求：
- 规则族在所有步骤和热身中采用固定的开发/验证分配。
- 与 Skill 的 val 分开。
- 每轮一个候选，从选中的现任 Rubric 继续。
- 在相同输出上用固定分母比较：检出、误拒余量、覆盖率和最低证据量。
- 选择与授权分别记录。
- 轮数事先定死。
- 跨步骤合并验证行**不能**同时充当未用过的证据。

L2 需要自己的新验证器和学习版本。
