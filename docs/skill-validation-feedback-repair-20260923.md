# 2026-09-23：父 Skill 来源、判分审查与反馈—修订诊断

本报告对应新的 `development_repair_20260923_a`。历史 V16、9/22 自然实验、原评分及候选均不修改。本轮是**已消费开发集上的事后诊断**，不是正式泛化、Research 增益或部署安全性证明。

## 1. 父 Skill 到底从哪里来

父 Skill 不是手写文本：来源是 V16 的 `h0-r0-fixed`，GLM-5.3（PJLAB，temperature=0，low reasoning）从空 `parent_skill=""` 生成。当前父文本 3,706 字符，与原 API 回执逐字相等，Skill、请求、回执、更新、checkpoint 和冻结记录的哈希均吻合。

但其依据很窄：只有 `exclusive-prefix-products` 与 `strict-increase-streak` 两道合成 Python 修复题，每题两个公开例子。四条 no_skill/current 轨迹不是四条独立学习历史，因为初始两角色都没有 Skill；四条额外探针记录均为 `not_detected`。父文本总结了局部修改、输入保持和文件分节交付等经历，其中来源任务约定不适合直接提升为通用规则。

选择规则是预先指定“第一条历史、第一轮、fixed 分支的更新”，不是看新实验成绩后挑出的父 Skill。**来源可追溯不等于质量已经验证。**

来源文件：

- `outputs/skill_validation/natural_20260922_bigmodel_c/parent_skill.json`
- `outputs/coevolution_v16/pilot_20260915_a_clean_resume_20260916/learning/h0-r0-fixed.json`
- 同一 V16 目录的 `api/calls/b1e3e2e652b9a8f7a2f5e624a10d592e8a72333bf1f2acc5476305daa38bf0b6.json`
- 来源导入规则：`skillopt/skill_validation/single_round_data.py` 的父版本冻结函数。

## 2. 当前判分不是“全靠固定答案”，也不是官方完整 EvalPlus

可见验证 V 使用公开契约和样例，执行后形成反馈。隐藏审计 H 运行候选代码和冻结的参考实现，在 `base_input` 与 `plus_input` 上比较输出；参考答案会随输入执行计算，不是只比较一个写死的数值。

H 路径在 `natural_data.py` 的 `_AUDIT_PROGRAM`，并未直接执行原始 `row['test']` 脚本，所以这是自定义差分审计，不能宣称官方全榜成绩。`pass` 只表示这些检查通过，`unknown` 不等于语义失败。

需要保留的边界：

- 有限样例不能穷尽正确性，参考实现也可能不符合题面。
- `/116` 的负数示例与参考实现冲突；`/151` 的 bool/int 约定不明确；`/76` 的零底数零次幂需要显式约定。这些任务原始 H 分数保留，诊断另加 `contract_review_required`，不根据新分数删题。
- 旧公开例提取器存在遗漏。已有覆盖清单和修正适配器仍显式版本化，不悄悄改变旧产物的任务哈希。
- 当前只检查已声明的义务，不把父 Skill 的“输入永不变化”等习惯添加为题目新要求。

**不建议用一个 LLM judge 替换可执行测试。** 更合适的分工是：LLM/Rubric 审查题意、检查依据、适用条件与歧义；Research 在确有外部知识缺口时补充资料；可执行检查给出行为观察；独立审计评价验证器。冲突应保留为争议、unknown 或待人工裁决，不能让 judge 自动改写标准。

这一建议也与 [EvalPlus 的执行测试思路](https://github.com/evalplus/evalplus) 一致；[LLM-as-a-Judge 原始研究](https://arxiv.org/abs/2306.05685) 明确讨论了位置、篇幅、自我偏好与推理能力限制。它不说明所有 LLM 评审都无效，而是说明评审器同样需要独立校准。

## 3. 本次实际改动

| 模块 | 改进与边界 |
| --- | --- |
| `development_feedback.py` | 全部 development 配对通过旧回执重放；汇总每个任务、每个 repeat 的公开 V 状态；固定分层选详细案例；所有提示按总 120,000 UTF-8 bytes 限额。H 不进入更新器。 |
| `public_revision.py` | 所有条件使用同样的新初稿提示；实际公开检查后至多一次修订，可 KEEP；保存初稿、修订稿、阶段回执与失败原因；对无回执中断 fail closed，不丢弃已完成修订。 |
| `development_repair_study.py` | 仅加载旧 development，读取冻结的真实候选并去重别名；独立目录保存新候选、初稿/修订成绩与成本；新代码完成公开修订后才读取 H 评分。 |

公开执行或 API 不可用、解析失败、KEEP、合法修订分开记录。合法修订即使变差也保留，不根据 H 或公开分数偷偷取两次中的最好答案。无安全执行器时不会退回本机直接执行候选代码。

### 全量反馈回放的实际输出

旧 updater 输入是 8 题、首次重复、双方全部 public pass，收到 0 个回归信号。新反馈覆盖 **64 题 × 2 次 = 128 对**：

| 公开 V 关系 | 配对位置数 |
| --- | ---: |
| Current 回归 | 4 |
| Current 改善 | 3 |
| 共同失败 | 0 |
| 不确定 | 1 |
| 共同通过 | 120 |

这些是**公开 V**而不是 H 的统计，不能与原 9 个 H 回归混为一谈。完整摘要保留所有 128 对；预算内保留 10 对详细案例，其中 3 对回归、3 对改善、1 对未知、3 对共同通过。第 4 个回归进入全量摘要但没有完整源码细节，不能声称每个失败均完整送入模型。

实际提示长度：evidence 114,963 bytes；contract_only 53,597 bytes。后者独立选择最多 16 个公开契约，不读任何执行结果或依据执行结果选题。本轮不能声称两个更新对照使用相同实际 token 成本。

### 新候选文本的独立审阅（不根据本轮分数选结论）

- evidence 新增“先直接实现定义、优化前验证等价”，确实受到 `get_max_triples` 公开失败影响。但失败实质是分组数量偏移；反馈中也有正确的闭式公式，因此不能将失败归因为“闭式方法不好”。候选提到的 `missing cross-term counting` 没有对应证据。
- `iscube` 的两个负数错误已进入详细反馈，但新 Skill 仍主要泛泛提醒“检查负数”，没有明确归纳符号归一后保持比较一致等可操作规则。
- contract-only 自行引入“冲突时 benchmark 断言优先”的一般规则，公开材料并未授予这种普遍优先级。
- evidence 仍将“不修改输入”写得过强，未完整保留旧 fixed 中“任务允许或要求修改”的例外；当前失败没有为这种收紧提供证据。

因此，反馈接通和文本发生变化不等于正确归纳、可靠接受或泛化已实现。这两份新文本只作为冻结的诊断候选，不自动进入部署。后续规则级审查应同时利用失败与**正确替代解**，避免只从错误案例得出过强规则。

真实修订阶段也已观察到反例：`coverage_contract_only_u0` 在 `/116` 的第二次生成，初稿用 `(位数, 数值)` 排序、公开检查和 H 都通过；修订却删掉数值这个第二排序键，公开检查与 H 都失败。这一具体退化违反题面明确的同位数数值排序要求，不能因为该题另有负数约定争议就把它也解释为评分争议。记录保留在 `positions/21c9df0a80aa4105a93021c27de66e425f648d1037093f6ec468e2fc87f73849/`，不从原始修订统计中剔除。

### 可以得出的结论

1. **公开执行—修订链确实产生了实际修复，但不是只增不减。** 112 个位置共 10 次 H fail→pass、1 次 pass→fail。No-Skill 全部 KEEP；25 个位置实际改写代码，86 个 KEEP，1 个显式 API 失败回退。不能把不同条件和重复采样合并后当成 112 个独立任务，或用这些次数声称统计显著。
2. **旧父 Skill 在这批回归诊断题上依然弱。** 修订后 7/14，对 No-Skill 有 5 负、1 胜。来源很窄、部分规则越界是可核查的质量风险；但本轮没有逐条删除规则的因果消融，不能把每个随机推理错误都归因于 Skill 文本。
3. **全量反馈接通了，但独有收益尚未成立。** 新 evidence 修订后 11/14，优于 Current 的 7/14 和新 contract 的 9/14，却没有超过 No-Skill 或两个旧 contract 候选的 11/14。它对 No-Skill 的 1 胜、1 负都发生在 /76 的两次重复上，逐题通过率与 No-Skill 完全相同。它和新 contract 初稿都为 10/14；后者最终落后主要来自 evidence 修复一次 /77、contract 改坏一次 /116。本轮只有各一个新候选，提示长度和实际计算量也不相等，因此不能把差异归因为结构化反馈的稳定优势。
4. **评分边界仍然影响解释。** /151 在所有条件下均为 H fail，是共同问题而非本轮 Skill 特有回归。独立检查其 16 个位置、17 个实际产物，均显式排除 bool；H 均为 base 7/7、plus 997/999，疑似同一类型约定冲突。汇总回执未列逐例失败输入，尚不能严格断言两条失败都且仅由 bool 导致。/76、/116、/151 的预先记录争议均保留，不能事后按有利口径删题。尤其 /116 的那次删排序键是真实公开契约退化，不能用该题其他歧义将它掩盖。
5. **这不是跨域泛化评测。** 任务来自已经消费、按历史回归选择的 development；新反馈也包含这些开发任务。新求解器从一开始知道有一次公共检查与修订机会，不能与旧的单次生成成绩作单变量因果比较。没有读取 final、没有新增 Research 对照、没有批准候选部署。

### 完整性与成本

- 226 个逻辑请求、226 次 HTTP 尝试、226 份终态回执；无悬挂请求、无自动重试。
- 2 次 Skill 更新、112 次初稿生成、112 次修订请求；模型回执合计 **366,780 tokens**。
- 1 次修订输出达到 2,048 tokens 上限而截断，显式保留初稿；没有补采样。对应新 contract 的 /116 repeat 0，初稿 H pass 得以保留；它不是前述 repeat 1 的语义退化。
- 111/112 个修订机会完整完成；所有 112 个最终产物有明确 H pass/fail，本轮 H unknown 为 0。**终产物有判分不等于修订请求全部成功。**
- 两个更新调用实际消耗：contract_only 14,335 tokens，evidence 32,982 tokens；同预算上限不等于等实际成本。
- 独立复核确认结果文件与 112 份 position 记录逐项一致，条件集合与冻结候选一致。

## 5. 测试与 review

主线测试已运行：`python -m pytest -q tests/test_skill_validation_*.py`，**1,142 passed**。随后连同历史 `tests/test_validator_pilot_*.py` 回归，**1,472 passed**。工程 fixture 与真实模型诊断严格分开。

## 6. 下一步应改什么，而不是如何继续堆运行数

本轮已解决“失败反馈根本没有被看见”“建议验证但实际无执行机会”“旧 Candidate 未覆盖回归题”三个工程缺口，但没有解决 Skill 的可靠机制归纳和广泛有效性。

优先推进：

1. **局部种子与规则级证据约束。** 从预登记的多条真实开发轨迹生成多个 local seed；每条新规则绑定失败证据、正确替代解和适用例外。禁止凭一例失败推出“所有闭式方法不好”“不要求修改就永不能改输入”等普遍规则。现有父 Skill 保留作弱种子对照，不能根据新成绩替换历史起点。
2. **修订的可采纳性与公开不回归检查。** 对明确的公开检查退化，可以在新版本协议中研究“拒收修订、保留未污染初稿”；依据必须是可见 V 而非 H，所有条件采用同一策略。当前原始修订统计保持不变，不能事后回选最好答案。
3. **评分口径先明确，再用独立任务确认。** 契约冲突由可追溯的审查处理，运行标准化执行评测并保留与本轮自定义 H 的差异。随后在预先冻结的新任务上比较多父版本、多个 updater 样本及 Near-Miss；继续报告逐任务胜负、覆盖和成本。LLM judge 适合辅助审查规则成立条件，不适合替代能执行的正确性检查。
