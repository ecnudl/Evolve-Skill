## Deviations (with reasons)

1. **Registrar-assigned ids.** The registrar assigns new and revised ids (`p-<bench>-<k>-<n>`, or `fx-` for
   engineering-fixture evidence, next free n). The manifest carries no id for them, so C1 never fails on id
   spelling, and lineage is set by the registrar.
2. **Executed check order.** The order is C1, C2, C4 (static bans on the source), C3, C5, C6, C4 (leakage and output
   bans), C7, C8, C9. Each result is reported under its registered id, so C4 can appear twice. `Procedure` refuses
   any policy violation, static bans included, and notes exist only after the C6 replay.
3. **Test trajectory reference.** A replay test's `trajectory` is the stored trajectory's cell id, not the plan
   example's path form.
4. **`note_matches`.** It takes ordered literal fragments rather than a regex: a model-written regex could backtrack
   catastrophically on the host.
5. **Non-vacuity.** `withheld_expect` is fixed to false. A test is non-vacuous when its property is false with the
   procedure withheld (the differential test) or under its declared mutation. `applies_*` tests need a mutation,
   since withholding never runs the predicate. The mutation set is registrar-defined (ticket A10-1).
6. **ALFWorld state-facts contract.** It is registrar-defined (ticket A10-1). Agreement is counted over the steps
   after which `alf_after_step` ran; with no comparable step, the check fails.
7. **Public-view subtraction in C4.**
   - Notes are checked against their own item's public text. On ALFWorld that is the step's initial plus current
     observation.
   - The description and the literals are checked against the public texts of the items the change's replay tests
     cite.
   - `absent_findings` wraps `leakage.findings`, using `_grams`, `_numbers` and `normalize` read-only.
   - All hits share one adjudication call; each flagged text is sent once, bounded at 4,000 characters.
8. **Option-letter ban.** The "choose by option position/letter" ban is an output check on LiveMath notes
   ("option/choice X", or a line holding only a letter). It is not a code analysis; the adjudicator prompt covers
   the rest.
9. **C8.** C8 checks that no shown note carries `<answer`, `</answer`, `<action`, `</action`, `<calc`, `</calc` or a
   code fence. The system prompt is not an input of any hook, so its hash is unchanged by construction, and it is
   not compared again.
10. **C9 cap fault.** C9 also reports `note_over_bench_cap`: a single note over the bench's per-request cap, which the
    shell would always skip.
11. **One record per step.** One sealed `engineer` record per step holds every change's check reports, instead of
    separate check records.
12. **Describer behaviour.**
    - `describe` returns the sealed record rather than bare text.
    - It makes no call for a procedure without a note hook, since T_F shows nothing where F shows nothing.
    - A long text is cut at the last sentence end inside the band; a short one is kept and flagged `short`. There
      is one call only.
    - Lexicon sentences are dropped, because the shell shows T_F text unscreened.
    - The cap is the smaller of the declared note cap and the bench caps.
13. **Signatures.**
    - `zero_crash` takes the procedure, loaded alone via `solo`, and the in-scope inputs. Seed 0 runs forward and
      seed 1 in reverse.
    - `fix(ctx, change, report)`, `run(ctx)`.
    - The re-propose call adds `"unparseable": reason` to the user message.
14. **Shown trajectories.** Only `arm_kind == "parent"` trajectories are shown to the engineer; run-slice card cells
    are not. All stored run trajectories in scope are replayed.
