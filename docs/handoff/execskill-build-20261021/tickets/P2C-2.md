# Ticket P2C-2 → registrar (then I1): the read gate is re-applied on every relaunch, also after the read started

From P2C, 2026-10-22 16:xx. Pre-existing behaviour, not changed by P2C; row 8 makes the gate larger for chain G.

§9.3: "the test read starts only when ..." 1.3 x the estimate is left on `<c>:solver` and `<c>:test`.
`chain.run` calls `read_budget` every time it reaches the read: on the first launch, and on every relaunch after a read
unit paused (a `recover` + relaunch). `read_budget` compares the remaining budget with 1.3 x the WHOLE estimate (chain G:
x max(1, factor_G)), even when some read units are complete and their tokens are already settled on `<c>:test`.

Example: the read spends 60M of `<c>:test`'s 99M and one read unit pauses (P4 sandbox). After the owner's `recover`,
the relaunch finds 39M left < 1.3 x 54.4M = 70.7M and pauses with `test_read_budget`, although the paused unit needs
far less. Only a cap raise (no CLI yet, runbook row 10) lets the read resume.

Options:

1. Gate only the read's start: skip `read_budget` when `test-read.json` is absent but any read unit already has an
   attempt or a `unit.json` (the read has started), or record the first gate in a write-once `read-gate.json` and reuse
   it.
2. Gate the rest only: 1.3 x the estimate scaled by the read units still to run.
3. Keep it (a relaunched read always needs the full margin) and tell the owner that a paused read unit may need a raise.

The gate record (`test-read.json` field `gate`) is written only when the read completes, so the chosen option should
also say what is recorded for a resumed read.
