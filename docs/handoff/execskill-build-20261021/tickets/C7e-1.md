# Ticket C7e-1 → registrar (or the integrator): G_acc cells are charged to the acceptance scope, the registration puts them in the examiner scope

From C7e, 2026-10-22. Found while checking that the redo sub-scope agrees with calc T6 and S-E6 (ticket C7c-2).
No code changed for it. Low severity at the pilot's sizes: every cap still holds at the maximum schedule. Only the
1.5x margin shrinks, and the examiner scope is reserved but never spent.

## What the code does

- `acceptance.schedule` (acceptance.py:191) puts the G_acc jobs in the acceptance round, in their source item's
  block. Each generated item runs on S', S, P_y and C, plus S_dup when the generator was admitted after step 1.
- `step._accept` (step.py:786) runs every job of the round through the accept endpoint (`st.solver("accept", ...)`,
  step.py:796-797). So G_acc's cells are charged to `<chain>:xs:<bench>:<k>:accept`. Since C7e, the G_acc cells of a
  redone block are charged to `...:accept:attempt-N` and `<chain>:redo`, like the rest of that block.
- No code charges a G_acc cell to `...:examiner`.
- In v1 only OfficeQA (and LiveMath in the formal chain) has G_acc. `step._g_acc` returns None on SpreadsheetBench
  (registrar decision on ticket C1-3).

## What the registration says

- §3.3 (registration line 318-320): "它的做题费用记在考官作用域里（9.2、9.3）".
- §9.2 assumptions (line 807): "考官作用域 = 难度带探针 + 捷径探针 + G_acc（每道 A\* 题 1 道，S'、S、P_y、C 各 1 次；
  OfficeQA 另加重复组 S_dup）".
- Calc T6 and the `protocol.STEP_CAPS` comment (protocol.py:470) say "run / examiner (incl. G_acc) / self-test /
  acceptance". `protocol.MAX_SCHEDULE_CELLS` (protocol.py:486) counts G_acc in "examiner": OfficeQA (110, 290) =
  band probe (0, 90) + shortcut probe (60, 0) + G_acc (50, 200). "accept" (200, 1400) does not include G_acc.
- S-E6 (`smoke._scope_cells`, smoke.py:1053) prices the scopes from `MAX_SCHEDULE_CELLS`. It therefore agrees with
  the registration, not with what the code charges.

## Size (OfficeQA step 2, maximum schedule, high anchor 7,927 tokens, procedure arms x1.6; my arithmetic)

| Scope | Registered max (high) | What the code charges at the max | Cap | Cap / max |
|---|---|---|---|---|
| `...:officeqa:2:accept` | 19.34M | 19.34M + G_acc 2.93M = 22.27M | 29.5M | 1.53 → 1.32 |
| `...:accept:attempt-N`, one block (C7e) | 9.67M | 9.67M + 1.47M = 11.14M | 14.8M (redo reserve) | 1.53 → 1.33 |
| `...:officeqa:2:examiner` | 4.55M | 1.62M (G_acc's 2.93M never charged) | 7.3M | 1.6 → 4.5 |

G_acc at the maximum is 50 items x (C as a card arm + S', S, P_y and S_dup as procedure arms) = 250 cells:
50 x 7,927 + 200 x 7,927 x 1.6 = 2,932,990 tokens. That is 15.6 % of the accept round's 1,600 cells.

## Choices

1. Follow the registration. In `step._accept`, run the G_acc cells through an examiner endpoint on the kind scope
   `...:examiner`, whichever accept attempt runs them. Two things are needed: `acceptance.runner` picks a context by
   cell set, and `units.solver_endpoint` takes an examiner endpoint outside the examiner unit. S-E6 already matches.
2. Re-register in v1.1, before the pilot. Move G_acc from the examiner rows to the accept rows of
   `MAX_SCHEDULE_CELLS`, recompute the T6 caps (accept up, examiner down) and the redo reserve (one block with its
   G_acc). S-E6 follows from `MAX_SCHEDULE_CELLS`.
3. Keep the code and document the mismatch. The caps hold at the maximum schedule either way.
