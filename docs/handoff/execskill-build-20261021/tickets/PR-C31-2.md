## Why

`evaluation.unseal` now scans the whole run root for every registered canary before the chain's first unseal
(`_root_scanned`), and the canaries come from two sealed records in the run root: the S0 record
`shared/test-canaries.json` (`protocol.CANARIES`, copied by `make-manifest`) and the test read's
`shared/test-read-canaries.json` (made by the first read child, `evaluation.make_read_canaries`). The e2e's `pilot`
fixture writes neither, so since PR-C31 the fixture **errors at its unseal loop**:
`ValueError: No registered test canaries in the run root` (on the shared tree as of 13:40; the file's sha256 then was
`2896c548…a9a3ae`, mtime 10:34).

## The patch (validated on a throwaway copy: `11 passed in 314.77s`; earlier recorded runs 321-330 s)

The fixture writes an S0 record (stand-in texts for SearchQA and ALFWorld), and the OfficeQA read child makes the
read record before `evaluate`, as `evaluation.run_unit_spec` does, then reads with the merged canaries. Every stand-in
text has the OfficeQA test pages' one length, so the root scan hashes one window length (no measurable time). The
fixture's OfficeQA questions repeat four templates of the training pages, so `canary_panel` offers each test page's
context as its question text (otherwise every test question is also a training question and the scan hits).
