# Ticket C5-3 → registrar / owner: v1.1 note items from C5 (safety findings 3-5, statistics findings 6 and 8)

From C5, 2026-10-22. These are readings C5 had to choose while implementing the registrar decisions of 2026-10-22.
Each is implemented as described and covered by tests. Each needs a line in the v1.1 note, or a different ruling.

1. **J5 start-balance guard, re-derived (statistics 8).** The order is now one uniform seeded order per block, as
   registered. Under that order the registered statistic fails the 5 % band by chance in most rounds (ticket A9-2:
   P = 0.62-0.99 for 30-300 cells per arm). The guard therefore decides on `spread_s`: the spread of the arms' median
   start delays, where a cell's delay is its actual start minus the start at its place in the block's seeded order
   (the block's k-th earliest start for the k-th cell). It fails when an arm was sent out of its seeded place, for
   example held back by a slot or resumed after a pause. The registered statistic is still recorded next to it as
   `raw_spread_s`, together with `order_spread_s` (the part that the seeded order alone explains). Code:
   `acceptance._balance`.
2. **J7 probe block (statistics 8).** The probe items are dealt over the blocks in turn, in their seeded order, and
   interleaved in each block's one order. LiveMath has one acceptance block, so in v1 this only removes the separate
   "first block".
3. **SearchQA carrier (statistics 6).** "The carrier yields a non-empty answer" is read as: the frozen extraction
   (last `<answer>` tag, else last non-empty line) is not itself a JSON object, and its frozen SQuAD normalisation is
   not empty. So the closing line of a ```json fence, or the `}` that ends a multi-line JSON object, holds no answer,
   and the JSON channel decides. J4's format flags still read the tag only (unchanged).
4. **Container names (safety 3).** The registered `--name execskill-sbx-<uuid>` becomes
   `execskill-sbx-<chain>-<unit12>-<uuid4>` for tagged workers (ticket A5-2, option 2).
5. **"3 tries, 10 s" (safety 3).** Read as: 3 tries of `rm --force` plus an exact-name check, each command bounded by
   `CLEANUP_SECONDS` = 10 s, with tries 1 s apart. The worst case is about 62 s. fixer-9 proposed a 60-120 s window.
   The latency of every confirmed removal is recorded (`Worker.cleanups`).
6. **Restart once (safety 5)** is per call. A call whose container docker reports OOM-killed, or which vanished while
   docker and the image are present, gets one replacement container and one retry, with the procedure still loaded.
   A second loss is P1, and the procedure is dropped. Docker not answering, or the image gone, is P4. A worker that
   died in a container still present and not OOM-killed, or a stall, stays P1, as registered. One start retry, which
   covers the 20 s ready ping, comes before P4.
7. **Residual: OOMKilled is container-wide.** Docker sets `OOMKilled` if any process of the container was OOM-killed.
   An earlier call child killed by the memory cgroup (charged to that call as P1 `killed`) therefore makes a later,
   unrelated worker death read as "oom" and costs one extra retry before P1.
8. **Residual: process isolation (safety 4).** Call children run in their own process group. The group is killed at
   timeout and after every call, and children are non-dumpable (`prctl` through ctypes). The worker parent is
   non-dumpable and ignores SIGINT. Its ping reports `dumpable` (0, or None without prctl). Not covered: a descendant
   that leaves its process group, which needs `os` (banned by the hygiene layer), survives until the container is
   removed. S0 should record `dumpable` from the pinned image and add the escape-probe rows of fixer-9 item 2. They
   were not added (smoke/escape probe are A13's).
9. **Not changed:** safety review minor 17, a failed `fork` that ends the worker (it is still charged as P1 `worker`).
