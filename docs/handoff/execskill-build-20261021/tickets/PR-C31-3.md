# Ticket PR-C31-3 → registrar: four decisions the run-root canary scan needs before the pilot's unseal

From PR-C31 (ticket C3-1, option (b)), 2026-10-22 13:4x. Registrar decisions 2026-10-22, row "C3-1 canaries" (b);
registration §8.1, Codex F16 (§20). Implemented as registered (see notes/PR-C31.md); these are the points where the

## 1. A hit that is not a leak: how does the owner release it?

As built, a hit pauses (`<chain>/root-scan/attempt-N/status.json`, kind `canary_hit`); the owner's `recovery.json`
(`run_execskill.py recover`) only allows a new scan, which hits again unless the files are gone. There is no release:
a coincidental match -- a test text that also occurs verbatim on the training side, e.g. a templated question shared
by a training and a test item -- blocks the unseal for good (removing training records is not an option). The
fixture data shows the risk is real in principle: the fixture OfficeQA questions repeat four templates across training
and test pages (the e2e therefore feeds its test pages' contexts as the canary texts, ticket PR-C31-2). For the real
OfficeQA / LiveMath / SpreadsheetBench splits nobody has checked train-test duplicates of the canary fields (SearchQA's
S0 exclusion drops training items equal to a test question; the three other benches have no such step). Nothing
in the frozen loaders rules duplicates out: the OfficeQA and LiveMath panels rendered by coevo5 get one family per
item id (`coevo5/data.py:310`); SpreadsheetBench's importer derives a family from the exact normalised
instruction only when no family map is given (`continual_eval/datasets.py:305-312`, `:470`). Not checked further.

Options (PR-C31 recommends (a) + (b)):
- (a) Selection skips test texts that occur verbatim in the same field of the bench's training-side items (the run's
  pools, checked when the record is made, under the read consent; training data is not test data). About 10 lines in
  `select_canaries` / `make_read_canaries`; changes which texts are chosen (still seeded and deterministic), so it is a
  registration change.
- (b) An owner release: a `recovery.json` whose decision is `release <scan record_sha256>` lets the next unseal accept
  exactly that scan (same hits), and the unseal marker names the release. About 15 lines in `_root_scanned`.
- (c) Keep as built: every hit is a stop, resolved outside the protocol.

## 2. The text kinds of the second record

Built: OfficeQA `question`, LiveMath `question`, SpreadsheetBench `instruction` (the public field the solver sees as
the task; `READ_CANARY_SOURCES`, evaluation.py:127). Not the OfficeQA context pages: training and test items may cite
the same Treasury Bulletin pages (not checked), and a shared page would not be a test-only text. Please confirm.

## 3. Cost of the scan

The scan hashes every window of every distinct canary length over every distinct text of the run root (a repeated text
of at least 256 characters is hashed once). Measured on dl (one process, machine shared): a synthetic 25.5 MB tree
(1440 files, 60 contexts each repeated 12 times) with 25 canaries of 25 lengths took 105 s; one process hashes about
1.5 M windows per second. The pilot root's size is unknown; v3's run root `/data/coevo5-20261017-run` is 1.5 GB in
143K files. If the pilot's distinct text is a few hundred MB, one scan takes hours, and each chain's first unseal
scans the whole root (twice in all). The e2e is unaffected (one window length; 11 passed in 314.8 s vs 321-330 s
before).

Options: (a) accept the time (it runs once per chain, before the readout); (b) a process pool over files (about 5x on
dl's 7 CPUs); (c) one scan per run root shared by both chains when both ended before the first unseal; (d) a rolling
64-bit fingerprint stored beside each sha256 prefix, so the scan runs vectorised and only candidates are sha256-checked
(about 50x; changes the canary entries of both records and `make_canaries`, so a registration and CLI change).

## 4. Where the record is made

The decision says "at the start of the pilot's test read ... before the first evaluation unit". Built: the first
`evaluate-unit` child (any bench, either chain) makes it under a lock after `consent()` and before its own attempt;
every other read child waits on the lock and checks run and consent. So no read unit evaluates a test item before the
record exists, but the record is made inside a read child, not by a separate step before the children (reasons: the
child already checks the consent and holds the manifest and the panel reader; doing it in `chain.evaluate` would open
three test panels in the chain parent process, and a CLI step would be one more owner action). That child also renders
the OfficeQA and LiveMath test panels once more (minutes at most). Please confirm or ask for a separate
`make-read-canaries` CLI step (I1).
