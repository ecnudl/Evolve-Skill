# Ticket C7e-2 → owner: a redo after a round has finished all its blocks changes nothing (J5/J6 "undetermined", or a decide error)

From C7e, 2026-10-22. This behaviour is new with the one-block redo (ticket C7c-2). No code changed for it. The
owner needs to decide whether it is wanted.

## What happens now

The redo rule (registration §9.3, "暂停只重做一块"; owner decision #15, a block is redone whole and never spliced)
keeps every block that an earlier attempt completed (`acceptance.earlier_blocks`, acceptance.py:357). A round can
pause after its last cell. Two cases:

- J5 or J6 fails. `decide` returns `undetermined`, the decision is written in the attempt, and `acceptance.settle`
  raises `Pause("acceptance_undetermined")` (acceptance.py:291-292). Registration §6.4: J5 "否则暂停"; J6
  "p < 0.01 → 暂停（交错或确定性坏了），不出决定".
- `decide` raises after every cell was stored, for example "Too few answered items for the t-test".

In both cases every block of attempt-1 is complete. When the owner writes `recovery.json`, attempt-2 reuses every
block. No cell is sent, and `decide` makes the same decision (or raises the same error) from the same records. The
unit pauses again and has used one of its `MAX_REDOS = 2` redos.

Before C7e, the whole-round redo re-sent every cell of the round in the new attempt, so it could produce a different
decision.

## What the registration does not say

§9.3 registers a redo for a pause inside a block. It does not say whether the owner may re-run a finished round after
J5 or J6. Either way has a cost:

- J6 means the interleaving or the determinism is broken. Re-running the same code would not fix that, and changing
  the code is a new protocol version.
- A fresh round would send the same A\* items again after the owner has seen an undetermined result (a second look).
  It also needs a whole-round budget, not the one-block sub-scope `...:accept:attempt-N` (calc T6, redo reserve =
  one block). That brings back the problem of ticket C7c-2.

## Choices

1. Keep it (the default now). A J5/J6 pause, or an error after the last cell, is final for that round. The runbook
   should tell the operator not to write `recovery.json` for `acceptance_undetermined`, because the redo only
   reproduces the pause. The owner then decides what happens to the step (archive S', stop the chain, or start v1.1).
2. Register a "fresh round" redo for these pauses only. For example, a recovery decision field makes
   `earlier_blocks` keep nothing, the redo runs every block, and the caps are re-registered at whole-round size
   (or the owner raises them with `raise_cap`). This needs a v1.1 registration and the second-look caveat in the
   report.
