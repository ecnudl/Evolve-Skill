## Choices

1. **Row shape.** `Rule` is a namedtuple. Its first seven fields are the row of spec/engineer.md 1.1 item 4:
   `key, rule, sentence, rewrite, legal, illegal, parent`. An eighth field, `label`, is appended. It is the name
   printed in brackets (`[module_level, statements]`) or after "Rewrite," (`word set`). The spec's tuple has no
   place for it. A rewrite row has `sentence` None; a parent row has `rewrite` None.
2. **Rendered once at import; checked again by `verify()`.** The texts and `RULES` are rendered once at import from
   the bound modules, and `system()` returns those. `verify()` renders again (private `_rules()`, `_render_all()`)
   and compares the new rendering with the stored texts and with `PINS`. So a bound value changed after import, a
   changed text, or a changed pin all make it raise. The monkeypatch test uses the private renderers to show that
   the text follows the bound values.
3. **Pin keys.** `PINS` is keyed by `(bench, purpose)` tuples, as in the spec. `verify()` returns JSON-friendly keys
   `'<bench>.<purpose>'` for the manifest.
4. **`POLICY_VERSION` is computed here.** It uses the same expression as `W:37`, because this module must not import
   `writers` (import order `replies <- engineer_prompt <- writers`).
5. **NOTES caps come from `notes.FIELD_TYPES`.** This follows DESIGN's "every list and limit in the text is
   rendered". It adds `notes.FIELD_TYPES` to the frozen names read. The text states one cap for "facts" and
   "warnings", and a test asserts that the two are equal.
6. **`CHECK_WORDS`.**
   - Rows are `{'rule', 'rule_text', 'rewrite'}` per check.
   - The rule names are `no_hook_function` (DESIGN) for `hooks`, and `structure` and `source` (the check names) for
     the other two.
   - The `hooks` rule text is word for word the HOOKS sentence of the system text; its `%s` is filled with the
     bench's note hooks.
   - Every other word is new wording. It enters the fix user message, not the ten pinned texts, so the test pins it
     literally.
7. **`screen_evidence` details.**
   - Check `policy` re-runs the screen and ignores `failed['detail']`, as the spec says.
   - It raises ValueError when the screen finds no violation or the source is not text. Such a call is a caller
     mistake that cannot happen with the same source and version.
   - For the other checks a text detail passes through. A list of rows (the `hooks` shape of spec change 7) gives
     the `detail` texts of its rows joined by `'; '`.
8. **`rule_key_for` gets the full stripped line, not the cut one.** So a long word-set constant whose `.split(` lies
   beyond column 240 still gets `constant_word_set`. The row shows the line cut at 240.
9. **Line numbers.** They follow the Python tokenizer: `\r\n`, `\r` and `\n` are line breaks. I checked that a lone
   `\r` counts as a line break for `ast`, and that `\x0c` and ` ` do not; `str.splitlines` would differ.
10. **Added `evidence_record(evidence)`.** It is not in the DESIGN list. It gives the record form of spec/engineer.md
    3, `{'rows': [{'rule', 'key', 'line', 'detail', 'source_line'}], 'more'}`. `key` is found from the rewrite text,
    which is unique per row (`verify()` checks this). For the other checks `key` is the check name. So 4b can store
    the record without calling the screen again. A rewrite that is not a row of this version is a ValueError.
11. **Example programs.** Every example defines `before_call`, so it would also pass 4b's hooks check. The syntax
    lines sit inside `before_call`, as in the spec table. The `constant_regex` examples start with `import re`,
    because the legal form needs it. The size and constant-size examples are sized from the bound limits.
12. **`verify()` is not memoised in the module.** The tests need it to recompute. The memo at the top of
    `propose_programs` belongs to W (4b).
13. **`MACHINERY_SYMBOLS`.** It lists every frozen name the module reads, in the shape of `machinery.REQUIRED`, as
    `replies` does. A test compares it with the actual attribute reads.

## Disagreements

1. **The [import] sentence states a permission the screen does not grant.** DESIGN's sentence says `"from M import
   name" are allowed for them`. The screen also rejects, with rule `import`, a from-import of a member that the name
   or attribute rules ban, including `time` and `random`. Checked on the real screen:
   - `from datetime import time` gives `import: datetime.time`;
   - `from pandas import read_csv` gives `import: pandas.read_csv`;
   - `from numpy import random` gives `import: numpy.random`.

   The import row's rewrite ("leave type hints out ...") does not fit these cases either. Implemented: the DESIGN
   text verbatim. It is the binding wording and it is safe, since the screen is unchanged and the error costs at
   most one fix call. Proposal for the coordinator or the Codex review, as a new `PROMPT_VERSION` with new pins:
   append to the sentence `, except a name banned below (from datetime import time is rejected: import datetime and
   use datetime.time)`.
2. **(Minor, as specified) the rewrite for some `attribute` violations does not fit.** `rule_key_for` maps
   `attribute` violations of `now`, `today`, `utcnow`, `sympify`, `parse_expr` and `lambdify` to `attribute_data`,
   whose rewrite is about data access. The checker reports these names under `attribute`, not under `clock` or
   `sympify`. The rule text (the attribute sentence, which lists them) is right; only the rewrite does not fit.
   Implemented as specified. A later version could map them to the `clock` and `sympify` rows.
