## Choices

1. Decision records name the arms `baseline` and `candidate_arm` (`{unit, arm, shared_from}`): DESIGN 4.1 says
   `candidate = {unit, arm}`, but a program record's `candidate` is the slot (DESIGN 3.2, 4c, its tests); one key
   for every kind. `baseline_selected` is in every comparison (true iff the baseline runs are a `cand_card` arm's).
2. A gate-accepted program whose description failed keeps typed-v1's `accepted: False, reason: 'description_failed'`
   (consumers read `accepted` as "installed") and stores `gate_verdict`; `chain.recompute_decision` restores it before
   `gates.recompute`. Every other record satisfies `gates.recompute(r) == r` directly.
3. `mark_infrastructure_reruns` moves the record instead of copying it: the file count is the re-run count, a stale
   infrastructure record can never come back as cached, and no record is archived twice.
4. Shared arms search the step's arms of the same bench in run order; the first equal arm is always one with its own
   runs. A shared gate-only unit has `plan.json` only and is marked done in the state.
5. `plan.json` stores per-item identity digests (sha256 of the canonical identity) besides `identity_sha256`, so a
   stored arm can be re-registered without recomputing a scratch type map; extra pause `gate_plan_changed`.
6. Gate counts in `decisions.json` are runs (`cells` = n * R) with `repeats` and `source`; the typing evidence gains
   `repeats`, `se_points`; a skill's origin gains `repeats`, `se_points` (programs `gain_points_fired`, `fired_items`).
7. `test_typed2_base.py`'s golden runs: DESIGN 4.2 (8) changes those requests on purpose, so `GOLDEN_RUNS` is re-pinned
   to the 5w tree (3.13 and 3.10 equal); 5b's cdf85b6 values stay in `GOLDEN_RUNS_CDF85B6` as history; the test adds
   the R-identical-requests and label checks. The test name still says cdf85b6 (not renamed, so no test disappears).
