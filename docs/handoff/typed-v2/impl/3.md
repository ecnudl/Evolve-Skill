## Choices

1. "Equal texts count once" compares texts with surrounding whitespace removed; the returned text is the first
   candidate in the order inline `source`, inline `code`, fences (inline plus an equal fence returns the inline
   text, as the frozen reader does; `source_from = 'inline_and_fence_equal'`). The echo rule uses the same equality.
2. `source` and its alias `code` are both candidates when both are non-blank: two different programs there are
   `ambiguous_source` (the frozen reader silently prefers `source`).
3. Rule 8 S2/S3 read as one order: a single owned non-blank block is returned; with no owned block the non-blank
   inline text; several owned non-program blocks are `no_source` even beside inline text (S3 names them without a
   condition).
4. Counts: a fix reply is checked only for exactly one change (`fix_change_count`, also for 4 changes); a proposal
   for at most 3 (`too_many_changes`).
5. Several JSON blocks: first the single one with `changes`, then the single one with `changes` or `change` (so every
   reply the frozen v2.9.3 rule reads is read). Outside the fences: two or more parseable balanced objects are
   `several_manifests`; a top-level scalar is `no_changes_key` naming its JSON type; a top-level array is always a
   bare list (non-object elements are `change_not_object`); an explicit empty list, `{"changes": []}`, is readable.
6. A nested envelope (`{"x": {"changes": [...]}}`), which the frozen reader relocates, is `no_changes_key` here: the
   design's envelope list is closed and the format retry covers it. Not a well-formed reply.
7. Kinds: a fix is always kind `new`; `read_fix` raises `ValueError` (caller mistake) for a change under repair whose
   entry states another kind. Non-new kinds come back with the raw entry minus `source`/`code` and the resolved kind,
   no source, no normalisation (the frozen reader normalises them; `W` drops them as `kind_not_new` either way, so
   they are not in the parity set). A new change reusing a parent id inherits nothing from that parent (DESIGN rule 9
   `inherited=(fix_entry or {}, {})`; the frozen reader inherits parent fields there).
8. Problem records carry the raw change object as `entry` (None for a non-object) and no source, as the frozen
   reader's error rows do.
9. Repair rows: the frozen source rows (`inline_source`, `source_block_selected`, `inline_code_alias`,
   `inline_source_unfenced`) and `unknown_key_ignored` for top-level keys beside `changes` are written too, in the
   frozen order, so that a well-formed reply's rows equal the frozen reader's. New reply-level rows
   `fence_not_program_ignored` and `fence_unassigned_ignored` (the second is a name added here) list dropped or unowned
   code blocks with number, length and sha256, so that every text not chosen is recorded.
10. `read['ignored']`: `from` is `inline`, `inline_code` or `fence <k>` (k counts code blocks only, as "fenced block
    k" in the sentences); `why` is one of `not_program`, `echo`, `same_program`, `ambiguous`, `unread`.
11. `manifest_json` does not carry the frozen parser message (it can hold a memory address); its reason comes from a
    strict `json.loads` (fixed messages, line, column; counted in the reply itself when there is no fence). The json
    module words a trailing comma differently on 3.13 than on 3.11, but `tolerant_json` reads trailing commas, so
    that text appears only beside another error; one run uses one interpreter.
12. Format retry: a previous reply above 200,000 bytes is `skipped: reply_too_large` WITHOUT spending the budget; a
    retry reply that is delivered but still unreadable becomes the outcome (`request_sha256` = the retry call), a
    retry without reply keeps the first reading and call; `read_with_retry(None, ...)` returns `result` None, no
    retry. The request is canonical JSON in the form of `writers._json`.
13. Pins live in the module (`PINS`, `computed_pins()`, `verify()` returning the names that differ) and the same
    values in the test; a test checks `FORMAT_RETRY_SYSTEM` and both `REPLY_FORMAT` texts word for word against
    DESIGN.md.
14. Test independence from files other steps edit now: the screen test calls the frozen `policy.check` (the check
    `writers.build_procedure` runs) instead of `writers`; typed-v1's `DEFAULT_PROGRAM` literal is copied instead of
    importing `T/smoke.py`.

## Disagreements

1. Block ownership (DESIGN 3.3 rule 7). Reducing the code blocks to the program blocks before A1/A2 makes a
   well-formed reply whose second program has a syntax error (two changes, blocks [program, broken program]) give
   `blocks_not_assignable` for both changes: the correct first program is lost, and a format retry cannot repair a
   syntax error. The frozen reader reads that reply by position, so the design rule contradicts the step's acceptance
   "well-formed replies give the same records as the frozen reader". Closest safe reading, implemented: one extra
   step A2' after A1 and A2, before A3: when the reduction dropped blocks, ALL code blocks are assigned by position to
   the changes without a program inline source if their numbers are equal. The broken block then reaches the screen
   unchanged and gets its fix call. Parity cases `broken_sibling_block` and `inline_sibling_and_broken_block` match
   the frozen reader; `test_a_block_is_never_forced_on_a_change_with_its_own_inline_program` shows that a change with
   its own inline program never receives a block through A2'.
