## Choices

1. **`no_reply` (4b's seventh status) gets a zero-call decision row with reason `'no_reply'`** (4b's proposal). DESIGN
   3.2 lists only three unpromoted statuses; without a row a step whose writer never answered would show no program
   decision at all. The reason is the status, as for `kind_not_new`, so that `screen:` keeps meaning "refused by the
   static screen" (typed-v1 wrote `screen:no_reply` in a `program-1` unit).
2. **The unreadable code is parsed from the row's reason.** The row keeps no problem dict, only
   `'unparseable: <code>: <sentence>'` (4b); `reason.split(': ', 2)[1]`. A reason of another form gives
   `'unreadable:' + <whole reason>`: a zero-call record never pauses the chain over a text format.
3. **Every send of every attempt stays in the programs unit's calls file** (DESIGN 3.3), done in `C.programs` with
   `_keep_earlier_sends`, because `role_call` builds a new `units.CallRecorder` for every attempt and its first flush
   would replace the earlier attempt's sends (4b, "Left for later steps" 4). It changes no request, no ledger charge
   and no other unit: the card writer and describer units keep the typed-v1 behaviour (DESIGN's sentence names the
   programs unit only). It relies on the recorder's public `out_path` and `sends`; a call without them is untouched.
4. **The chain reads `proposals.json` strictly** (`_check_proposal_rows`). DESIGN is silent on validation; a slot
   beyond `max_program_candidates`, a slot on an unpromoted row, a promoted row without its procedure or an unknown
   status would otherwise run a wrong unit (DESIGN: "no `program-3*` unit can exist"). A refusal pauses the chain
   (`exception:ValueError`) before any program unit; `proposals.json` stays as evidence.
5. **Decision order = row order**; zero-call rows are not written to any unit directory. They live in
   `decisions.json` only and are recomputed from the write-once `proposals.json` and the same snapshot on resume.
6. **`max_program_proposals` is not read by the chain.** The writer's signature has no such parameter (4b Choice 8)
   and its reader caps the records at `profiles.MAX_CHANGES` = 3; the key stays recorded in `decisions.json` limits.
7. **The scripted program writer is stateless** (chosen by the request JSON), so a resumed unit gets the same
   replies; the promotion path runs on `PROMOTION_BENCH = 'searchqa'` (the first bench of `ORDER`, and the bench of
   every one-bench fake smoke in the tests) and follows spec/engineer.md change 13 together with spec/reply.md's
   scripted retry: 3 calls in one unit. `DEFAULT_PROGRAM` stays a plain string (the canonical one-proposal reply
   that tests pass explicitly). Scripted entries use `max_note_chars` 600 and leave `state_bytes` out.
8. **The e2e's zebralogic step takes the promotion path** (searchqa keeps the canonical reply, so every step-1 pin of
   the e2e stays). This makes the end-to-end run cover a format-retry lineage and a zero-call row through the
   closed readout, as spec/engineer.md 4 asks ("the lineage hash may be a fix or retry call").
