## Choices

1. **`chars` in the skill record.**
   - The typed-v1 skill record has no `chars`. Its origin keeps a five-key decision summary built in `C.make_skill`.
   - DESIGN 3.1 ("chars means content characters everywhere (attempt row, card decision, skill record)") and the
     ACCEPT both name the skill. spec/card.md 3.1 says the skill shape is unchanged; DESIGN takes precedence.
   - Smallest change that meets them: `make_skill` adds `chars` to `origin['decision']` for card skills only.
   - Unchanged: the program skill records, the card body, the skill `sha256`, and every request (the describer,
     selection and engineer index never read `origin`).
   - This edit is in `make_skill`, one function beyond the named `card_decision` site, because the skill record is
     built there.
2. **`card_limits` is a copy** (`dict(cards.LIMITS_RECORD)`), so a consumer of the result cannot alter the module
   constant. The test checks that it is equal to the constant and is a different object.
3. **One screen call per attempt.** `write_card` calls `cards.card_screen` directly, as spec C4 asks, rather than
   calling `screen_card`, which returns the key only. `screen_card` stays public but nothing calls it.
4. **Where the golden comes from.**
   - The coordinator named `git show HEAD:skillopt/execskill/typed/writers.py`. The test reads the same file by its
     git blob id, `646346d0…`: `HEAD:…` at 8375ecb, unchanged since 9ca2754, sha256 `39368635…`.
   - The blob id stays valid after the build's later commits; `HEAD` will not, because then it would compare
     typed-v2 with itself.
   - The test checks the sha256 of the source. It runs the source as a sibling module of `T/` and puts nothing in
     `sys.modules`.
   - Where git or the blob is missing (for example a copied tree on dl), the live test skips. The pinned digests,
     produced by that writer, then still prove the byte identity.
5. **Golden inputs are literal.** The scenarios use literal examples (not `outcomes_for_writer`) and a literal
   round-2 `result`. That result has no `kind: card`, so `revision_result` passes it through unchanged. The pins
   therefore depend only on the card writer and the bound v2.25 texts; Step 5's change of the gate decision record
   does not move them.
6. **Chain-level evidence.** The new chain test sits in `tests/test_typed_chain.py` next to the fake writer. It
   implements spec/card.md section 4 ("add one assertion that decision `chars == len(text) - 1`"), widened to the
   attempt row and the skill as the ACCEPT asks. Both the real-writer path and the fake-writer path are covered.
