## 1. B7 -- the C3 format predicate is the scorer's own extraction

### 1.1 Finding (v3 tree)

`REQUIRED_FORMAT["searchqa"] = REQUIRED_FORMAT["officeqa"] = ("answer_tag_present",)`: some `<answer>...</answer>` tag
exists (`checks.last_answer(output) is not None`), even an empty one. The frozen scorers read differently:

- SearchQA (`backends.score` -> `skillopt/envs/searchqa/evaluator.py::evaluate` -> `extract_answer`): the last tag's
  stripped text if any tag exists (no fallback, even when it is empty); without a tag the last non-blank line; else
  `text.strip()`. So a tagless reply whose last line is the answer is read and can pass (C3 counts it a violation),
  and an empty last tag yields `""`, EM 0 (C3 counts no violation).
- OfficeQA (`backends._score_answer_tag`): the last tag's stripped text (same regex and flags as `checks.ANSWER`);
  `valid = bool(text)`; no tag or an empty one is `invalid_format` 1.0 and a fail (C3 counts the empty tag as none).
- LiveMath: `answer_single_letter` equals the scorer's validity (same last tag, upper-casing, one trailing `.`/`)`/`:`
  dropped, one letter A-E) -- already agrees; tests pin it. SpreadsheetBench `code_present` / ALFWorld `()`: a
  program the code extraction cannot find (`code_delivery:...`) or a malformed action (`invalid_action_format`) is
  the decision table's `malformed` kind (row 6, `outcomes.MALFORMED_PREFIXES` / `MALFORMED_REASONS`), which C3
  already counts; unchanged.
- `scoring.lenient` (§5.9, descriptive) reads `last_answer` too: a tagless SearchQA reply the scorer reads (and may
  pass) is lenient-`False`. (v2: kept as registered; B7 does not cover it, §1.2.)

### 1.2 Design

- `checks.scorer_answer(benchmark, output)`: the text the benchmark's scorer extracts, `None` when it extracts none
  (blank = none). SearchQA calls the scorer's own `extract_answer` (imported from `skillopt.envs.searchqa.evaluator`,
  a light module scoring.py already imports), so the predicate cannot drift from it; OfficeQA/LiveMath use
  `last_answer` (the same regex, flags and strip as `_score_answer_tag`).
- `checks.answer_extractable(benchmark, output)`: `True`/`False`, `None` for a non-text output (the caller decides:
  `step.violations` counts `is not True`, `diagnose_one` pre-empts on `is False` -- both as today).
- It is a C3 check, not a rubric check: it lives in `checks.FORMAT_CHECKS`, not `CHECKS`, so `checks.validate`
  refuses it in a rubric and `texts.RUBRIC_SYSTEM`'s literal library list stays exact. `checks.run_format(name,
  benchmark, output)` runs a `REQUIRED_FORMAT` name (a `FORMAT_CHECKS` entry, else the library check without
  parameters). `checks.FORMAT_MEANINGS` gives the analyst a per-bench meaning of the code.
- `REQUIRED_FORMAT`: SearchQA and OfficeQA -> `("answer_extractable",)`; LiveMath, SpreadsheetBench, ALFWorld unchanged.
- Callers: `step.violations` and `examiner.diagnose_one` call `run_format`; `examiner.code_meanings` reads
  `FORMAT_MEANINGS`. The smoke's format check uses `step.violations`, so it follows (docstring only). Cards unchanged
  (they still ask for the tag); no prompt changes.
- Not changed (v2): `scoring.lenient`, the registered §5.9 diagnostic (registration 20261016 §5.9 and row 19: "只看标签内、
  单一答案"). B7 asks only that C3's predicate and the card wording agree with the scorer; `lenient` has no production
  caller (only `tests/test_coevo5_core.py`). Aligning it is an owner option (§6 Q7), not part of B7.
- The analyst's meaning of the SearchQA code says only what the scorer did not find ("the reply's last <answer> tag is
  empty, or the reply is blank"); v1's parenthetical on the last-line fallback is withdrawn, because the frozen SearchQA
  card the analyst also reads says the tag's text is compared and the rest ignored (§1.6 Q2).

Consequences (state them in the delta): C3's extra-violation criterion no longer counts a tagless SearchQA reply whose
last line the scorer reads, and counts an empty (or blank) last tag on SearchQA and OfficeQA. A failed tagless SearchQA
answer goes to the diagnosis model (it was coded `answer_tag_present` by format); an empty-tag failure is coded
`answer_extractable` by format. The smoke's SearchQA floor now detects only empty/blank extractions (§1.6 Q1).

Token effect (diagnosis model, GLM): a failed tagless SearchQA answer now reaches the model diagnosis (up to G4's three
votes plus re-asks) and an empty-tag failure on SearchQA/OfficeQA leaves it; both stay inside G6's bound for diagnosis
(items x 3, at most half the panel failed), so no GLM cap changes.

## 2. B11 -- the training side excludes items whose candidate read view the scorer cannot verify

### 2.1 Finding (v3 tree)

`qualify.qualify` scores every item twice with its own reference workbooks as the answer. `sheet_recalc.evaluate_pair`
recalculates the reference first and then the prediction (here the same file: a cache hit inside the scoring
directory), so an item whose REFERENCE read view is unverifiable is already excluded today (`reference:` + a
`READ_VIEW` reason -> `read_view_unverifiable`). The items B11 means pass that check: their failure is on the
PREDICTION side, for workbooks written as programs write them. `sheet_recalc_v7.Recalculator.run` returns
`general_formula_read_view_unverified` when `_formula_view` raises: every formula cell of the workbook (not only the
answer cells) whose original style is General and that Calc date-formats needs a numeric cache in the export and an
exact formula-text binding. An openpyxl-saved input breaks that for some items, so a correct answer there is
`prediction:general_formula_read_view_unverified` -> the decision table's artifact kind -> token `unknown_artifact` ->
`stats.bounds`: a fail in L for a rule arm, a pass in H for the parent. v3's qualification never scores such a
workbook, so it cannot see them.

### 2.2 Design: the candidate probe (training side only)

- After all reference scorings, every item whose references passed both scorings gets ONE more scoring, with its
  candidate probe (`qualify.probe_prediction`): for each case, the case's public input workbook (the bytes the
  solver's sandbox receives, `backends._xlsx_bytes`) loaded and saved by openpyxl with default options -- as a
  solver's program does -- with every answer-range cell (`spreadsheet_compat.resolve_targets` on the reference's
  sheet names, `_legacy()._iter_cell_names`) set to the reference workbook's content (`data_only=False`: a formula as
  its formula text); a missing target sheet is created. That is a correct answer as a program writes it.
- The probe is scored like a reference scoring (a new position: request `scoring` = `qualify.PROBE` =
  `"candidate-probe"`, its own scoring directory and `scores/<position>.json`, under `native.hold()`, `_check` rows 1
  and 3: a configuration error or an unconfirmed cleanup stops the qualification as before).
- Outcome per probed item, recorded as `{"outcome", "reason"}` under the record's `probe.items`: `pass`;
  `candidate_read_view_unverifiable` (some case reason is `prediction:<r>` with `r` in `PROBE_EXCLUDES` = `READ_VIEW`,
  the named switch) -- the item is EXCLUDED with that category; `fail`; `unknown`; `unavailable` (the probe could not be
  built, e.g. a merged answer cell or a missing reference sheet: nothing is scored). Only the read-view outcome
  excludes.
- Record (train side): `excluded` gains `candidate_read_view_unverifiable` entries, `counts` runs over
  `TRAIN_CATEGORIES` (the four v3 categories + the new one), new key `probe = {"candidate": PROBE_CANDIDATE, "items":
  {...}, "openpyxl": <version>, "python": <version>, "scorings_per_item": 1}` with `PROBE_CANDIDATE =

  reference scorings (v2: the probe's single scoring is counted in `probe`). Which items the probe excludes depends on
  the host openpyxl that saved it (the probe runs in the `qualify-train-sheet` process, not the manifest's), so
  `prelaunch.generate` requires `probe["openpyxl"] == manifest.environment()["openpyxl"]` (Q10), next to the existing

  configuration reason at the probe (for example `native_scoring_input_error:*`) still stops the qualification and

### 2.7 Open questions (B11)

1. Fidelity (the mechanism decision). The probe stands for "a correct answer as programs write it": host openpyxl,
   default options, the reference's cell content (formulas as formulas). It can miss items where solvers write
   differently (values where the reference has formulas, other libraries, `_xlfn.`/boolean spellings) and it cannot
   exclude an item that only some answers make unreadable. Recommendation before freezing v4: on the development
   machine, run `qualify-train-sheet` with the v4 code into a new directory and compare its excluded list with v3's
   run evidence. v2: this replay is a gate before freezing v4. Pass criterion: every v3 training item whose cells
   were `unknown_artifact` with `prediction:general_formula_read_view_unverified` in all arms comes out
   `candidate_read_view_unverifiable`. If any does not, the host probe is not used and the sandbox-built probe (a
   fixed host-written program run by `backends._native({"operation": "spreadsheet_generate", ...})`, the solver's own
   openpyxl) is built instead, at the cost of a literal serialiser and the container path. Record the outcome (the
   matched and missed item counts, the new qualified count and `(t_k, t_b)` next to v3's) in the delta. The fake-scorer
   tests show only that the probe code works on real data shapes, not that the real v7 scorer path
   (`sheet_recalc_v7._formula_view`) flags the probe workbook; only the replay shows that.
2. openpyxl versions: the manifest binds the chains' interpreter and openpyxl (3.1.5 on this Mac); the solver's
   programs run in the sandbox image's. Check that the image's openpyxl matches the host's before relying on the
   probe (`docker run --rm <image> python -c "import openpyxl; print(openpyxl.__version__)"` on the dev machine).

   record whose openpyxl differs from the manifest's.
3. A `fail` probe (a correct answer compares unequal after recalculation) means the item can never pass in any arm
   (both a rule and the parent fail it: no bias, no information). B11's scope is the read view, so it is recorded,

### 3.2 Design

- `backends.py`: `HISTORICAL_FRAMING` (the old sentence), `SKILL_FRAMINGS = {"sectioned-v1": <the v4 sentence>}`,
  `_framing(runtime)` -> the historical sentence without `skill_framing`, the named one, or `None` for any other value.
  `readiness` and `solve` refuse `None` (`invalid_skill_framing`) right after the layout check, as an unknown layout is
  refused; the guidance block is `"\n\n" + framing + "\n" + skill` (ALFWorld: `"\n" + framing + "\n" + skill`), placed
  exactly where today's is (after the contract in the contract-first layout, before it in the historical order). An
  empty Skill has no guidance block either way, and every caller without the key is byte-identical to today (the v3
  layout tests stay unchanged and green; `tests/test_weak_solver_probe.py` and the historical pilots keep the old
  sentence).
- `protocol.py`: `SKILL_FRAMING = "sectioned-v1"` and `"skill_framing": SKILL_FRAMING` in all five `RUNTIME` entries
  (ALFWorld included: its Skill has the same sections). The runtime is part of an evaluation's identity
  (`evaluation.py`, "the solver and the frozen runtime"), so no v3 evaluation is reused.
- `outcomes.CONFIGURATION` needs no entry: like `invalid_prompt_layout`, an unknown framing is refused by
  `backends.readiness` before launch (`prelaunch.generate`, `smoke.setting`, the baselines' readiness check); the
  registered value is valid.
- Frozen bindings outside coevo5 (checked): `backends.py` is one of the files `continual_eval.core.source_identity()`
  hashes, and `_solve_alfworld` is one of `scripts/prepare_long_alfworld.py`'s AST-compared `ALF_FUNCTIONS`. Both bind

  sources, assets, data or configuration changed; use a new run"), and `scripts/prepare_long_alfworld.py` refuses it
  in `prepare` (`_common`: "Frozen common source differs", before the AST comparison) and in `--check` (`load_plan`).
  Neither is a v4 path (coevo5 loads no continual-eval plan); those historical runs keep their frozen checkouts, and

- Protocol-integrity 6, the part "plus `prediction:`-side configuration reasons": no prediction-side reason can trigger
  the configuration stop today. `qualify._check` tests `reason in CONFIGURATION` on whole strings and
  `reason.startswith(CONFIGURATION_PREFIXES)` with the prefixes `public_input_or_runtime_error:` and
