## 怎么读这些数

1. **S_k 减 C 不是第 k 步造成的伤害。** C 是完整的历史任务卡，C0 只有格式块。C 比 C0 高的地方，S_k 减 C 自然是负的，那是起点差距。下表是 C 减 C0，区间不含 0 的有五处：

   | 链 | SearchQA | OfficeQA | ZebraLogic | 表格题 | ALFWorld |
   |---|---|---|---|---|---|
   | G | +1.5 [−1.0, +4.0] | −0.6 [−7.9, +6.8] | −4.0 [−12.7, +4.7] | +12.3 [+5.1, +19.4] | −0.7 [−10.3, +8.8] |
   | D | +2.8 [+0.7, +4.8] | +7.6 [+1.2, +13.9] | −3.0 [−8.4, +2.4] | −8.3 [−14.7, −1.9] | +18.7 [+3.1, +34.2] |

   判断某一步的效果，要看 S_k 减 S_{k−1} 和 S_k 减 C0。

2. **程序包没变的对比只测到重跑噪声。** 两条链第 1、2 步，D 链第 3 步，以及 G 链第 3 步除 ZebraLogic 以外的四个 bench，都属于这种情况。SearchQA、OfficeQA、ZebraLogic、表格题上这些对比的请求逐字节相同，“同请求记 0”的次分析全是 0；ALFWorld 是多轮交互，说明不变，但整段请求只有约四分之一完全相同，次分析不全是 0。

3. **偶尔有区间不含 0 的格子，是多重比较下的偶然。** 每条链约 40 个对比，例如 D 链 ALFWorld 的 S3 减 S2 是 +4.5 [+0.4, +8.6]，D 链 SearchQA 的 S3 减 C0 是 −1.8 [−3.2, −0.3]，两处用的都是同一份程序包。

4. **OfficeQA 的区间按起点读数的时间分半分层**，S 组之间的对比不完全对应（下文 F7）。均值和好坏平计数是准的。

5. **表格题判不了的格子，S 组算错，C 组算对**，所以表格题上的 S 减 C 偏向对 S 不利。

## 代码排查发现的缺陷（下一版 v2.26，配置 `main-v10`，在修）

第 4 步两条链都因代码缺陷暂停。之后做了两轮只读排查：先由 4 个排查代理分区查，每条发现再由独立的反方代理核实，未核实的 5 条又单独核实了一轮。除已知的 K1、K2 外，又确认 9 处：

- **K1**：上一步真正跑过接受评估后，交给工程师的“上一步故障题、格式违规题”是题号清单，而不是计数，于是每一次工程师调用都报错。G 链第 4 步因此暂停。
- **K2/F1**：斑马谜题程序的钩子在别的 bench 的步骤里被调用时，走到了没开诊断通道的工作进程上。D 链第 4 步因此暂停。同一个根因还出现在两处：一是跨 bench 的不伤害门；二是单元之外的立即接受选择和任务卡选择。第二处发生时整条链的进程直接崩掉，连暂停记录都没有。
- **F2**：算请求身份时只在 ZebraLogic 上带配置，SearchQA、OfficeQA、表格题的任务卡没算进请求身份，候选和现任看起来完全一样，卡片 0 格测量就被拒。线上 9 轮任务卡这样被拒。
- **F3**：跨 bench 门把现任程序自己的故障算成候选的伤害。一旦收下一个偶尔超时的程序，后面每一步都收不下任何东西。
- **F4**：持续学习指标里“只看变了的步”那部分，以历史任务卡 C 为锚，而不是起点 C0，会把起点差距错算成伤害，或者掩盖真实伤害。这次没有算这个指标。
- **F5**：工程师写的“排除 ZebraLogic”在非 ZebraLogic 步骤里被悄悄丢掉。
- **F6**：确认单元中断后续跑时，会重新执行钩子，并要求结果逐字节一致；一次偶然的超时就会让续跑永久暂停。
- **F7**：OfficeQA 时间分半的随机种子含读数事件名，各次读数分半不同，分层用错了时段。
- **F8**：诊断通道第一次配置时如果容器丢了，不走登记的重试和故障规则，变成只能由负责人恢复的暂停。

修复进度：已完成并提交 `f635f67`（分支 `research/exec-skill-v226`）。每个缺陷都有一个在修复前必失败的对照；端到端测试走完第 3 步收下、第 4 步收下、第 5 步导入、40 个读数单元全部完成。一轮 Codex 只读审查和独立的 Claude 审计又找到 13 处，大多是第一轮修复本身不完整或新带进来的，已全部修好；dl 上 Linux 全量测试又找到一处，已修。最终 dl 上 Linux 全量测试单独跑 9,473 项通过、1 项跳过。不经负责人同意不启动。
