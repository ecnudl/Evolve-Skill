# V17 独立科学审查（2026-09-17）

范围：只读核查冻结的 `skillopt/coevolution_v17/study.py`、`core.py`、协议、派生分析脚本，以及 smoke 的四份 Skill 更新记录和实际更新请求。没有修改运行源码、协议、分析脚本或原始证据；没有调用模型、重跑任务或用检查结果挑选正式实验条件。

## 总结

**未发现需要立即中止实验的严重 final／机制标签泄漏，亦未发现 gate 按最终答案挑选 Skill 的路径。** 两个主对照可以回答受限的探索性问题；不能把结果直接扩大解释为机制泛化、全面负迁移控制或协同进化已经成功。

当前读取的 Skill 文本来自 `outputs/coevolution_v17/smoke_20260917_a/learning/`。以下定性判断只描述 **smoke 联调**，不是 pilot 的结果，也不是行为效果证明。

## 两个主对照实际上识别什么？

| 对照 | 已控制的内容 | 能支持的解释 | 不能单独证明 |
|---|---|---|---|
| cross_raw − local | 相同父 Skill、更新器、更新次数、反馈题数及输出预算 | 将第二次更新的证据从 Coding 换成 Spreadsheet 的联合效应 | 同机制匹配的独立贡献、纯粹跨域多样性效应、对所有领域的泛化 |
| cross_structured − cross_raw | 同一批真实轨迹与事实；展平后的事实哈希相同 | 同事实的 JSON 组织／分组方式效果 | 有无 Rubric、正确诊断信息有无、Research 的效果 |

“普通反馈”本身已经包含结构化的 `closed_feedback`，不是未经处理的裸日志。结构化臂新增的是领域／任务／角色分组，而非更多错误诊断或更强 oracle。上下文长度和输入 token 不同，不能说严格等总成本。

## 三个主要科学局限

### 1. 跨域证据也可能只把专化领域换掉

本地分支与跨域分支的题目内容、难度、错误类型及表征同时变化。现有设计按协议可识别这项联合干预，不能区分“跨域机制抽象”与“针对新的 Spreadsheet 开发题专化”。Spreadsheet 已参加开发，最终新 Spreadsheet 题只能称未见结构族；只有 Rule 是未参与开发的领域。

这也是保留父 Skill、No-Skill 和全部 raw 候选的价值：既要看新域是否获益，也要看原有 Coding 能力是否丢失，而不是只看更新后的目标域成绩。

### 2. 结构化组织并不等同于高质量机制反馈

两个跨域臂共享完整事实，是合理的信息守恒消融。但这种组织变化没有加入跨域机制对应、原因核验或反例解释，分组也只面对一个反馈领域。因此无效果不能推出结构化诊断无用；有收益也不能宣称 Coding Rubric／DeepResearch 已带来泛化提升。

本轮明确不含 Research 干预或持续验证器更新，不应把 V17 单次分叉的结果称作完整协同进化结果。

### 3. 覆盖与统计仍只支持小规模、条件性的判断

pilot 最终每域四个结构族、三个学习历史。现有统计保留族内变体与历史，避免把它们当独立新题，方向正确；但 bootstrap 区间条件于这三条已观察历史，没有覆盖新训练历史的随机性，也没有多重比较校正。少量族上的窄区间或零损失不能证明总体安全。

Near-miss 主要指明确授权替换旧行为的任务，不等同于广泛的不同机制或无关任务集合。任务仍是统一受限接口下的合成修复任务，不能代表真实代码仓库、工作簿操作或开放式规则问题。

## 证据边界：哪些被隔离，哪些仍进入模型？

已检查的主路径具有以下隔离：

- 学习反馈投影要求 `phase=development`，确认集与 final 不进入 Skill 更新。
- 全部候选、历史及 gate 决策先冻结，之后才进行最终模型求解。
- Gate 使用独立 confirmation，不读取 final；所有被拒绝候选仍接受 raw 评测。
- 四份实际 smoke 更新请求中未发现 `mechanism_cell`、`mechanism_label`、`structural_family`、参考产物或隐藏测试正文的字段。

但存在一个需要准确说明的边界：**`closed_feedback.cluster_id` 仍嵌套在实际更新请求中。** `core.feedback_views` 只删除顶层 host-only 字段，而 V15 的闭合反馈包含族身份。因此不能写“所有宿主结构族身份完全不进入模型”。

此处没有泄漏 final 成绩或隐藏机制类别，也不是某一对照臂独有的信息；公开 `task_id` 本来还包含描述性的任务族名称。它不破坏这次 raw／structured 同事实对照，但后续若要严格匿名化结构族，需要另立版本并递归处理，不能修改当前冻结实验。

## Gate 保护与 Skill 泛化必须分开

部署映射只依赖可信环境 domain，不使用宿主 near-miss 标签逐题选择。Rule 一律 Base，所以 **Rule 部署成绩与 Base 一致是设计保证，不是学到跨域 Skill 的证据**。

部署指标从相同 raw／Base 抽样轨迹重放，不是新的在线试验。候选覆盖率为零时，只能说明没有部署候选；覆盖率非零时，也必须同时报告 raw 收益、残余损失及使用范围。相对 raw 候选减少损失可以描述为本次门控保护，但不能改称 Skill 内容泛化提升。

派生分析脚本目前明确保留这些警告，没有将回退成绩直接命名为泛化收益。仍应避免仅展示部署宏平均而省略 raw 表格。

## 失败归因口径需要补充说明

`Study._row` 将 `delivery_valid` 转为布尔值；`core._counts` 对 `artifact_valid=False` 优先计入 `delivery_failures`。因此未获得有效产物的 API unknown 也可能进入这列，真实 Study 路径中的 `delivery_unknown` 不会自然保留为 `None`。

这不改变 all-attempt 成功率分母，gate 也不会因 unavailable 结果批准范围；但 **`delivery_failures` 不能直接解释为 JSON／格式错误数量**。失败也可能是响应不可用、截断或合约拒绝。

保持原冻结统计不变。报告可以另按已保存的 runtime stages、`stage_api_ok`、`chosen_stage`、`rollback_reason` 和 API 回执增加归因表，明确原始交付失败列和细分原因的对应。修订阶段 API 失败后保留有效初稿的情况，也应与彻底无产物分开。

## 结果汇报建议

1. 先给 raw No-Skill／父 Skill／三候选逐域表，再给两个主对照；gate 与覆盖率单独列。
2. 增加逐 history 的 raw 主对照差值、逐域胜负和 Skill 文本差异，展示方向是否一致；不要把三个历史的逻辑位置当独立样本。
3. 分别报告语义收益、交付改善、API unknown 与门控保护，不把不同来源的改善合并命名为机制泛化。
4. 宏平均不超过 Base 时，不能宣称整体泛化增益；但仍可诚实描述某个未见领域或最差域的局部改善和相应代价，避免只用单一平均值判定研究价值。
5. 本次观察不改变 pilot 条件、任务或阈值。若结果支持更强的机制抽象设计，应在新协议与新最终集上验证，而不是回看本轮 final 后反复调整。
