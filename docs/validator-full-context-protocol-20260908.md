# 完整开发证据与明确部署边界：补充验证器实验

登记时间：2026-09-08 10:42 UTC 左右，主实验 v2 正在生成留出代码，但尚未查看任何留出答案、oracle 成绩或 judge 结果。补充修订只读取 dev；必须先冻结补充 Rubric，之后才能读留出产物作配对评估。

## 触发原因

v2 的统一 30000 字符开发上下文虽然保证了两臂相同，却将候选代码字段压到每条 400 字符、私有失败诊断压到 128 字符，许多关键代码主体没有进入修订输入。两个最终提案又因编号条目间插入空白行被严格协议拒绝。反馈提案还出现了要求读取 `development_failed_checks` 等部署时不可见字段的检查。

这些属于输入完整性、接口和角色边界问题，不能作为 Skill 或 DeepResearch 有效/无效的结论。v2 数据和失败提案原样保留，不修改原成绩；本补充实验单独建目录、单独记账。

## 统一的工程修订组合

两个补充修订臂同时使用下列设置，不选择某个臂享受额外信息：

1. 同一批固定 12 个原始 dev 案例的完整任务、代码、公开证据、旧判断和开发硬审计，不做字段截断；整个请求最多 180000 字符，超出则明确停止。
2. 修订系统消息明确部署边界：新检查只用于根据候选代码、可见契约和公开执行日志评价候选代码，不能要求部署时不存在的 dev 私有 oracle、旧判断或自我评分记录；格式/基础设施错误由编排器负责。
3. 最终新增检查在原严格校验前只删除空白行和行首末空白；不修 typo、不删除非空条目、不修改语义或 core，不抽到成功为止。保留原文和规范化文本。

这是一个工程设置组合，**不能把它相对 v2 的差异单独归因于“完整代码”**。新的反馈/资料两个分支之间保持相同组合、完整开发案例、模型和阶段输出上限，仍比较整条修订流程而非“仅增加引用”的纯消融。

## 调用与评估

- PJLAB `glm-5.3`、temperature=0、stream、reasoning_effort=low。
- 仅反馈和反馈＋同一组三份官方资料各 3 阶段、最终各 1 个提案，每阶段最多 4000 生成 tokens。记录完整共享开发输入哈希、每阶段真实成本及任何无效提案。
- 修订准备阶段是 6 个串行调用，可以与主实验的 4 并发代码生成并行，合计最多 5 个模型请求；不额外生成目标代码。
- 新 Rubric 冻结后，且 v2 完整结果生成后，才取同一批 56 个留出产物（48 个自然、8 个受控）。每个有效补充验证器评分两次，最多 224 个 judge 请求，4 并发；对照复用 v2 的同产物 V0 记录。
- 计划新增 230 次逻辑调用，独立上限 240、最多 720 次 HTTP 尝试。若两臂均无效则不冒充完整对照；保留失败。
- raw 与公共硬 Guard 分开，unknown、schema/API 失败、误拒绝与误放行分开；配对键、目标请求哈希、oracle 必须一致。
- 同一份代码的两次判断不当作两份独立代码；自然和受控分开，错误的独立任务/任务族数与重复翻转也要报告。
- 一个 Rubric 提案加两次 judge 不构成修订算法的多随机种子复现；不据留出成绩选择最终验证器，不晋级、不接回 Skill。

原 v2 的静态 Skill 扩样与重复分析不受此补充影响，仍按冻结协议完整报告。全部补充设计由开发诊断触发，不使用新的留出结果调参。
