# 扩样与重复运行：Coding Skill / Validator 冻结先导协议

日期：2026-09-08。本文件在新实验调用模型前写入；运行目录的 `protocol.json`、源码和任务哈希为精确版本依据。

## 为什么这次不再看一个小 batch 的胜负

上轮只有 3 个来源任务、每条件 2 个回答，且交付格式占据主要误差。这样既不能证明机制 Skill 有效，也不能证明它无效。本轮分离三种干扰：任务选择差异、同一任务多次生成的波动，以及同一产物多次评分的波动。

增加回答数不是增加同等数量的独立任务。我们将固定样本数、交错调用各条件、保留所有结果；不因中途领先、持平或显著与否停止或扩样。无法消除所有随机性，但可以测量它并限制结论。

## 本轮问题和边界

1. 采用原生代码交付、统一执行器后，冻结的机制 Skill 相比 No-Skill 是否存在可观察的行为差异？相比通用提示是否也有差异？
2. 大小为 5 的任务 batch 的表面方向，相比完整任务池有多不稳定？扩大任务数和重复次数分别提供什么信息？
3. 紧凑评分协议和确定性公共检查下，固定/反馈修订/资料修订的验证器在同一批新产物上表现如何？同一验证器自己是否反复改变判断？

这是**静态 Skill 条件和一次验证器修订**的前置诊断，不是完整 Skill 进化或协同闭环。固定 Skill 避免本轮再混入候选生成与选择随机性；但不能据其效果证明自动 Skill 进化算法有效。每修订臂仍只有一个提案，重复 judge 不等于多次独立修订训练。

## 数据、划分、条件与预算

- 32 个新编写的 Python 操作契约，8 个任务族，每族 4 个不同操作问题；不是仅替换输入数值的 32 个“独立”变体。
- 4 个完整任务族用于 development，另 4 个用于 holdout；每部分 16 个任务 ID。任务仍全部是 Coding，不声称跨领域。
- 这些是作者构造的语义诊断，不是新公开 benchmark 分数，也不代表随机抽取的真实软件项目。共享编写风格、执行器和任务模板的依赖必须披露。
- 每题有明确可见契约、起始代码、公开案例、参考实现和至少 5 个私有案例。三种预冻结控制为 starter/reference/preservation mutant，后者须通过公开和请求行为检查、破坏保护条件。先检查全部 96 个控制产物。
- 三个目标条件：No-Skill；通用谨慎编程提示；沿用上轮人工的 Constraint Preservation Skill。全部在生成前冻结，不根据新结果选取 Skill。
- 每个任务/条件固定 4 次模型请求：**32×3×4=384 个自然产物**。返回相同内容也原样保留。
- 所有模型调用使用 PJLAB `glm-5.3`，stream、显式 low 推理档位、temperature=0；不发送或假装保证独立 generation seed。temperature=0 也不被视为服务端逐次完全确定。4 个 repeat 是独立发出的请求标签，不是 4 个训练种子。
- 沿用长请求保守 4 并发。每个 repeat 内将任务顺序与三臂顺序固定随机化；以包含完整三臂的小块交错请求。solver 和 judge 的计划顺序保存。因为 API 并发与耗时，实际完成顺序未必相同。
- 准备工作成功后先做 2 个简短协议健康请求。目标输出上限 6000、judge 2000、修订每阶段 4000 tokens。模型请求预算计划 840，硬逻辑上限 900，最多 2 次传输重试/请求，因此最坏 HTTP 上限 2700。实际返回用量另记，预算不是账单保证。

## 交付协议和硬检查

目标返回原生 Python 或一个 Python fence，明确不要求大段代码嵌入 JSON。使用已测试的、只提取不改逻辑的提取器；允许的解析路径在第一次新回答前冻结。这不是在结果之后为某个条件放宽评分。

仍保留语法、AST、隔离执行和有限行为 oracle。分别报告：传输不可用、无法提取、语法/运行契约违规、可执行行为失败。API 或无法归责的沙箱资源故障不伪装成任务答错；同时报告缺失率及最坏情况界限，防止只看可用子集。

Judge 采用固定行协议 `DECISION=PASS|FAIL|UNKNOWN` 加 `EVIDENCE=...`，不用大段 JSON。核心请求/保护/产物完整性义务不可删除。额外保留一个不使用私有答案的 Guard：确定的交付、语法、AST 或公开测试失败由程序拒绝；未知基础设施状态不是确定性失败。

所有有完整目标响应的样本仍运行原始 judge，保存 raw 与 guarded 两套结果。因此本轮可以区分协议/硬 Guard 收益与软 Rubric 收益，但不声称实际在线节约调用。

## 验证器对照与 holdout 屏障

只取固定的 solver repeat 0 进入验证器审计，不按答对/答错选留出产物。每个任务族的第一个排序任务另加入 reference 与 preservation mutant。每个分割因此是 48 条自然产物和 8 条受控产物。

每个验证器对同一产物评分 **2 次**。dev 只有 V0，共 112 次 judge；holdout 在三个修订臂有效时共 336 次 judge。重复判断不是新的代码样本。

流程：

1. 先生成全部 dev 自然产物，V0 审计其中固定 repeat 0 与控制产物。
2. 每个 dev 任务族选择第一个任务的 reference/mutant，以及一个自然案例；自然案例按首个 V0 判断的语义误判、unknown、固定 ID/条件顺序优先。共最多 12 个案例。开发反馈允许包含本地私有审计，不包含 holdout。
3. 反馈臂进行 gap analysis → critique → final；资料臂进行 gap analysis → 官方资料 synthesis → final。均 3 阶段、同模型及阶段输出上限，输入 token 不保证相等。
4. 资料在模型调用前安全获取并冻结，限定 Python 官方 copy、sorting、dict 语义页面。通过现有受信本地代理、不改 Clash；失败则在准备阶段停止，不能静默变为无资料对照。本轮是 documentation-grounded repair，不是开放式自主 DeepResearch。
5. 两臂最终只能添加最多 8 条、5000 字符检查；核心规则由代码保留。格式和来源引用合法不等于评价有效。只有一个最终提案，不抽到成功为止。
6. **两个修订状态及 Rubric 全部冻结后，才开始生成 holdout 自然产物。** 对同一批产物交错执行所有有效验证器的两次评分；无效修订如实保留、不能冒充有效三臂比较。

六个修订调用共享**完全相同的开发案例内容**：开发部分最多 30000 字符，依据原始案例统一确定是否截断、字段限额及显式遗漏标记，保留全部已选 ID；不根据资料臂或阶段改变案例内容。每次请求校验共享案例快照，整体上下文最多 90000 字符；超出则停止，不偷偷减少资料臂看到的代码。实际截断情况须报告。本轮不晋级验证器、不反馈进已冻结的 Skill。

## 分析：先看配对结构，再看总体数字

Skill 的主要对照是 mechanism − No-Skill，通用提示为次要对照。先对同一 task/repeat 形成可用配对，再对任务求 4 次平均、任务族内平均、任务族等权平均。完整报告微平均、逐题、逐族和四个全局 repeat 的差异。

用固定种子、10000 次整任务族 bootstrap 形成探索性 95% 区间，重采样时保留族内任务和重复结构。**holdout 只有 4 个族，区间可能不稳定、离散甚至退化，不能作为总体安全或确认性显著性证据。** 不能把 384 条回答当作 384 个独立任务。

区间跨零只表示本轮无法区分方向，不表示无效。即使探索性 90% 区间落在预定 ±10 个百分点内，也只描述为当前选定任务池与该容差相容，不能宣告总体等价。边际优势、多个比较和样本天花板均须提示。

另在已经完整生成的矩阵中，固定种子抽取 5/10/20/32 个任务的子 batch，最多 2000 次、不放回，展示方向和分位数如何变化。这只是同一数据上的**条件重采样诊断**，不是新增实验或“Skill 真正有效的概率”。超出该分割实际任务数的 batch 大小不可计算。

验证器分别报告自然/受控产物的 TP、TN、FP、FN、合法 abstain、schema/API 错误、接受污染率、真通过接受率和覆盖率。额外统计同一代码两次判断的 pass/fail 翻转及任何方向分歧。比较对象固定；不能选取两次中更好的决定。

若自然的真实行为错误集中在少数任务，或几乎没有可执行行为错误，误放行率的证据仍很弱。小错误数、零误放行或大量 unknown 都不构成安全证明；受控变体单独报告，不冒充自然风险。

## 停止与下一步

不因成绩改变固定样本量。只因健康协议失败、隔离/来源准备失败、固定预算耗尽，或一个完整分割 repeat 波次中超过 10% 目标请求终止失败而停止；保留全部成功/失败缓存。后续修复要新协议/目录，不覆盖失败记录。

本轮如果区间仍宽，下一步应扩充独立任务族/真实项目，而不只是对同一题多抽几次。如果原生交付后依然天花板，则需要更难但契约明确的任务，不能把人工 Skill 在该任务池无提升推广为研究方向无效。如果验证器能稳定修复真实漏检且不过度拒判，再单独设计多修订种子和固定/动态验证器协同闭环。

方法参考：[Cameron & Miller 的簇相关推断综述](https://escholarship.org/uc/item/1jq5d0pq)、[Agarwal 等关于少量运行和不确定性报告的研究](https://proceedings.neurips.cc/paper_files/paper/2021/file/f514cec81cb148559cf475e7426eed5e-Paper.pdf)。这些资料不保证本轮四簇 bootstrap 的覆盖率或代表性。

## 运行前端错误修订：v1 → v2

2026-09-08 10:25 UTC 检查开发失败时发现：虽然 solver 系统消息要求原生 Python，任务模块的公共限制文本仍遗留 `Return exactly JSON {"code":...}`。这是本地实验构造的冲突，不应算作机制 Skill 的效果或单纯模型随机性。

因此通过 SIGINT 暂停 v1，等待当时批次的请求落盘后退出。保留 2 个健康调用和 90 个 dev 目标调用，共 92 次逻辑/HTTP 请求、97,114 个已返回 token，全部调用完成且无 API 终止错误。v1 没有生成 holdout、没有 judge 或修订调用，也没有完整结果。已查看的部分 dev 行用于定位该协议冲突，不能称作结果完全未被查看。

v2 只修正任务文本的输出条款，并新增冲突检查与版本标记；保持任务语义、起始/参考/缺陷代码、公开/私有案例、数据划分、三个 Skill 内容、样本数和统计分析不变。全部模型请求在新的缓存目录重新运行，v1 只记工程中止和成本，不与 v2 混算，也不据 v1 成绩选择任务或 Skill。原始源码与任务快照仍在 v1 目录中。

## 补充诊断登记：单轮 batch 与四轮平均的区别

2026-09-08 10:29 UTC，v2 仍在 development 生成阶段、尚未生成任何 holdout 或 Rubric 修订。代码审计指出：冻结分析中的任务子采样使用每题四轮平均，不能代表仅跑一轮的 5 题 batch。

因此在独立的完成后审计脚本中追加一项条件诊断：每次从已观测的四个完整 repeat 中等概率选一个，再不放回抽 M 个任务，对三臂同一 task/repeat 配对，记录方向和分位数；固定种子、每个 M 最多 2000 次。该脚本先检查完整结果屏障，不在完成前读取 holdout。

它与原四轮平均子采样分开报告，属于事后诊断设计（此前已看到部分开发和 v1 错误），不替换冻结主指标，不增加模型样本，也不是未来随机 batch 或真实收益的概率分布。

## 补充诊断登记：评分空白归一化

2026-09-08 10:35 UTC，仍仅有 dev 评分，尚无 holdout 产物。观察到紧凑行协议的部分无效输出只多出空白行，另有真正的 `EAVIDENCE` 拼写错误；某个空白行无效输出的语义判断本身还是错误的。

因此登记一个独立完成后敏感性分析：只删除纯空白行和各行首末空白，保留所有非空行、决定、证据和错拼写，再调用同一个冻结评分解析器。不得修正 typo、丢弃无法识别的非空行、改写判断或看 oracle 选择解析方式。raw/guarded 两种视角均与原严格结果配对；特别报告从 unknown 中显露出的误放行和误拒绝，而不只统计“恢复了多少合法格式”。结果不回写主实验、不计作新模型调用或新确认性证据。
