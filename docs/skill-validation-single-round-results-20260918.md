# 单轮 Skill 更新实验结果

2026-09-18。**真实模型实验已完成，反馈驱动的 Skill 内容更新链已接通；没有得到稳定的泛化提升证据。**

## 1. 做了什么

使用 PJLAB `glm-5.3`，并发 4，固定同一个历史 Coding 父 Skill，执行：

开发任务上的 No-Skill / Parent → 公开执行反馈 → 一次 Skill 文本更新 → 冻结候选 → 独立最终题目评测。

数据为固定版本 MBPP-sanitized 的静态兼容子集：8 道开发题、4 道验证器校准题、16 道最终题；最终每条件重复 2 次。排除了仓库历史已使用、已预留题及词面近重复族。**这仍是 16 个最终任务 ID，不是 32 道独立题，也不保证模型训练时未见过这些公开题。**

首条原生 assertion 对所有条件公开，其余断言与参考实现只在宿主独立审计使用。生成代码仅在远程隔离 Docker 中执行，没有在本机执行。协议与源代码在运行前固定，未根据最终结果换题或修改候选。

原设 fixed / adaptive_no_research / adaptive_research 三种反馈，但有效反馈相同，共享一个 updater 请求、产生同一个候选。因此下面只报告三个真实不同的条件，不把别名当三份独立研究结果。

## 2. 核心结果

| 条件 | 原生检查通过 | 执行后未通过 | unknown | 全部尝试成功率 |
| --- | ---: | ---: | ---: | ---: |
| No-Skill | 30/32 | 2 | 0 | **93.75%** |
| 原 Skill（Parent） | 26/32 | 4 | 2 | **81.25%** |
| 更新后 Skill（Candidate） | 27/32 | 2 | 3 | **84.38%** |

unknown 全是输出解析失败，不是已确认的语义错误；保留在全部尝试分母中，但不冒充算法失败。三个条件均无 API、SSH、超时或资源故障；16 份最终任务参考实现均通过原生测试。

候选相对 Parent 净增加 **1/32（+3.125 个百分点）**，相对 No-Skill 少 **3/32（−9.375 个百分点）**。只比较双方均可执行的配对：候选对 Parent 为 2 胜、0 负、26 平，另有 4 个未知配对；对 No-Skill 为 29 平、3 个未知配对，没有确认的新增算法胜利。

| 重复 | No-Skill | Parent | Candidate | Candidate − Parent |
| --- | ---: | ---: | ---: | ---: |
| 第一次，16 题 | 15/16 | 12/16 | 14/16 | +2/16 |
| 第二次，同 16 题 | 15/16 | 14/16 | 13/16 | −1/16 |

**两次重复的收益方向相反。** 一个学习历史、16 个任务不能证明稳定改善；temperature=0 也没有消除生成差异。本轮没有部署候选或扩大其 scope。

### 失败具体是什么

| 条件 | JSON／输出协议失败 | Python 语法错误 | 原生断言不通过 |
| --- | ---: | ---: | ---: |
| No-Skill | 0 | 2 | 0 |
| Parent | 2 | 1 | 3 |
| Candidate | 3 | 0 | 2 |

- 候选相对 Parent 的两次已执行胜利：`mbpp:413` 少了一个多余的 `}`，修复源码语法；`mbpp:63` 从有符号差 `a-b` 改为绝对差，通过原有隐藏断言。这是配对观察，不证明由某条 Skill 指令稳定导致。
- 候选相对 No-Skill 少的三个成功都来自 JSON 交付失败：未转义换行、返回 Python 代码块而非 JSON。不能说成已确认的推理能力下降。
- `mbpp:164` 有基准契约歧义：题面写“因数和”，隐藏断言要求 `are_equivalent(23,47)==True`，实际采用不含自身的真因数约定。Parent 与 Candidate 各两次均只失败于该第三断言。报告保留原成绩，但不能据此宣称 Skill 损害了数学能力。

## 3. Skill 真正改了什么，Research 起了什么作用

候选由实际开发产物与公开执行反馈生成，不是手写假候选。它减少了 `input_count/input_sum`、固定文件名等来源任务细节，强化“规格优先、公开例只是样本、检查未覆盖边界”的建议。

但它**仍保留**无条件“不修改输入”、强制 file-section、禁止 JSON 等旧规则，与本轮交付契约存在冲突；也没有明确的可执行 abstain 条件。因此，内容更新是真的，适用边界修正仍不充分。候选中的“构造 2–4 个边界例”只是行为建议，不能算作已经执行的新检查。

Research 本轮没有形成独立有效干预：

- 无 Research 自适应分支正常返回 `no_update`。
- Research 分支实际完成两次资料获取、两次模型调用；综合响应使用未加引号的 JSON 键，被严格解析器判为 `invalid`，按协议退回固定验证器，没有修补响应或追加调用。
- 更根本的限制在运行前已注明：当前只有三个预注册配方，这些 MBPP 契约没有输入保持义务或公开不变量，接口无法新增合法的有效检查。即使综合格式正确，也无法在本轮建立 Research 的增量能力对照。
- 两个自适应校准状态均为 `Pending/no_new_verifier`；而此面板也没有 Near-Miss，即便提出修改，仍不足以获得准入。所有候选始终是探索产物，没有 Skill 准入权。

**不能把 81.25% → 84.38% 归因于 Research，也不能把三条同分曲线作为三个方法的独立结果。**

## 4. 一个更有价值的诊断：高分可能漏掉什么

对开发题 `mbpp:643`，No-Skill 与 Parent 原本都通过全部三条原生断言。但任务要求检查 `z` 是否在**单词内部**，Parent 只检查整段字符串内部。

候选冻结后，另做了一个人工提出的事后容器诊断：

| 输入 `text_match_wordz_middle("abz.")` | 返回 |
| --- | --- |
| No-Skill 产物 | False |
| Parent 产物 | True |
| 基准参考实现 | False |

三次执行均正常，确认了原生检查的漏检案例。**它不是 Research 自动发现，没有回流 updater，没有修改原评分，也不是新的独立效果样本。** 一次样本不能建立 Skill 因果归因。

这解释了为什么不能只靠“扩大 batch”解决之前的高分问题：题目难度、检查覆盖、题面与测试是否一致、输出协议干扰，都可能影响测量。公开 benchmark 的原生测试通过也不等于完全正确。

## 5. 下一步应改什么

优先做两个小改动，而非扩大多轮协同进化：

1. **让反馈真正修正 Skill 的适用前提。** updater 不仅增加经验，还要明确处理“旧规则与当前任务契约冲突”，允许删除或条件化旧规则。把输出格式、输入保持等从全局命令改成由当前任务决定的要求。下一轮区分“仅契约条件化”与“条件化＋执行反馈”，避免把格式清理收益包装成机制泛化。
2. **让 Research 能把合理假设落成新证据。** 在受限检查规格中支持基于公开契约提出新的任务级输入／关系，而不是只能重跑原有例子。上述词边界案例可以作为工程回归测试；正式效果要用另外冻结的自然产物、合法替代解和 Near-Miss 校准，不能重复使用本轮已经看过的最终题证明提升。

之后才用独立 Skill Gate 评价是否值得提交、在哪些条件使用，再向跨域测试扩展。本轮仍只有 Coding，不提供跨领域泛化结论。

## 6. 工程交付与可回放性

- 新增 4 个小模块：`single_round_data.py`、`single_round_feedback.py`、`single_round.py`、`remote_executor.py`；复用既有 Research、Rubric、证据回执、校准和 Docker 执行器，未覆盖历史实验。
- 相关测试 **590 passed**；新增文件 Ruff 检查通过，Git diff whitespace 检查通过。
- 真实实验共 **125 次 API 请求**：120 次求解、4 次验证器提案、1 次 Skill 更新；全部由 `glm-5.3` 返回，无 HTTP 重试。记录 **133,206 输入＋10,428 输出＝143,634 tokens**。付费与执行主流程约 **6.8 分钟**，不含此前开发与测试时间。
- 额外事后诊断只增加 3 次隔离执行，0 次模型调用。
- 完整缓存回放时禁用了付费发送函数：新增模型调用 0；只执行一次无害环境预检；既有 **761 份 JSON 文件字节均未改变**，最终结果哈希一致。
