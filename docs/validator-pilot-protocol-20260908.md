# 验证器失准与一次修复：有界先导协议

日期：2026-09-08。状态：正式结果产生前的先导设计；具体任务、版本、参数、调用预算和文件哈希以运行目录中的冻结清单为准。协议或实现如需修改，应保存原版本，并说明修改发生在读取哪些结果之前，不能覆盖失败尝试。

## 研究问题与声明边界

本轮研究两个问题：固定验证器是否遗漏 Python 修复任务的真实错误；根据开发审计修订验证器，能否在新的任务上减少误判，且不过度增加误拒绝或拒判。如果 Skill 确实发生多个有效更新，再描述固定验证器在不同 Skill 版本上的判断变化。

这是 Coding Constraint Preservation 的小规模可行性实验，不是完整协同进化、跨领域安全认证、公开 benchmark 全量复现，也不是验证器随 Skill 进化必然失准的确认性检验。静态任务资料支撑的修订称为 **documentation-grounded verifier repair**；不能将其报告为已经证明自主 DeepResearch 的有效性或必要性。

预期有价值的结果包括正、负和无信息结果。全部回退、全部拒绝、评分文本变长，均不构成方法成功。

## 数据、预算与独立性

- 计划使用 9 个有公开来源依据的 Python 修复任务，3 个任务族各包含 3 个任务：LS4 为 train，LS5 为 development，LS3 为 holdout；任务族与分割完全绑定。记录来源、许可证、改编范围、可见需求、公开案例及独立的参考实现和私有案例。
- 每个自然任务、每个实际进入审计的冻结 Skill 版本生成 2 个执行重复；重复不是独立任务，更不是独立训练种子。
- `id`、`cluster_id`、`family` 分别记录任务、共同来源/依赖簇和任务族。由冻结清单报告真实簇数，不能将 9 个任务或其变体一律视作 9 个独立任务族。holdout 只有 3 个任务 ID，并且只属于 **1 个任务族**，不能声称跨多个独立留出任务族的统计泛化。
- 只使用 PJLAB 配置中的 `glm-5.3`。凭据只从本地配置读取，不写入协议、轨迹或报告。执行入口须保存实际模型、服务地址标识、采样参数、请求预算、时间和用量，不保存密钥。
- 正式运行前用小规模健康检查与逐档并发探测选择稳定配置；出现限流/错误时降低并发或暂停。没有授权也没有必要寻找极限。
- 正式逻辑调用数由实际保留的 Skill 版本数和受控产物数决定；少轮次时可能少于 300，包含全部候选、对照和 judge 时可能约 400 或更多。**准确上限以启动前程序生成的冻结运行配置为准**，不把粗估写成已实现的硬上限。模型任务、真实 HTTP 请求、SDK 重试、成功用量分别统计，不能把逻辑任务上限当作账单保证。没有预算余量时不自动追加实验。

## 可见信息与 oracle 隔离

目标模型和验证器只接收可见任务需求、起始代码、公开案例、候选代码及真实公开执行结果。不得接收参考实现、私有测试、私有期望输出或最终 holdout 审计结果。

固定验证器 V0 根据这些证据生成结构化判断。它可以依据代码作静态推断，不要求不存在的执行日志；不能将“未看到私有测试”自动等同于所有任务都必须拒判。也不能将声称检查过、输出很长或采用指定步骤视为正确性的证据。

私有 oracle 作为独立的影子审计：记录实际产物是否满足请求和保护条件。train 的 oracle 可以按下述预注册规则触发无学习空间停止；这属于 **oracle-informed preflight stopping**，必须公开说明。它不提供 Skill patch 内容、不作为 Skill 版本选择分数，也不参与 V0 的影子门判断。因此不能笼统声称整个实验从未使用 oracle 反馈。

development 的独立审计结果允许进入验证器修订输入。holdout 的审计结果不进入修订、模型选择或后续本轮 Skill 更新。数据角色不随观察到的结果改变。

## 流程一：有条件的短程 Skill 进化

1. 冻结任务划分、公开/私有执行规则、V0、起始 Skill、受控产物及分析规则；验证参考实现和执行器正常工作。
2. 在 3 个 train 任务上各生成 2 个 Base 自然产物。单独记录 API、解析和执行故障，故障不当作任务错误。
3. 若 Base 的 6 个 train 自然产物都通过私有硬验证，且不存在缺失执行结果，则触发预先规定的天花板停止：不继续宣称能从该来源集学习收益，但保留自然输出和受控产物的验证器诊断。该规则不证明总体 Base 完美。
4. 若存在可学习的自然错误，最多生成 3 轮 Skill 内容候选。Skill 更新仅使用当前 V0 的可见反馈及公共执行证据；候选生成、V0 影子门和版本保留规则必须在运行配置中固定。
5. 保存每个候选、是否实际改变内容、V0 决策及版本哈希。没有实质更新或持续生成无效候选时，不将轮次编号当作进化证据。
6. 无论天花板停止是否发生，均保留 Base 与一个预先冻结的人工机制 Skill，在全部 9 个任务上各生成 2 个自然重复。人工 Skill 是静态内容干预对照，不是学习成功，也不算自动进化轮次。
7. 冻结实际产生的 Skill 版本池后，统一进行 development/holdout 审计。所有版本使用相同留出任务与重复安排；结果不回传给已经结束的进化分支。holdout 产物可以提前生成并封存，但其评价指标和审计发现应在两个修订 Rubric 冻结后才读取。

固定任务上的版本变化仅是描述性证据。即使误放行增多，也不能仅凭本轮小样本断言 Skill 内生地诱发验证器漂移；需要排除模型随机性、任务构成变化和生成难度变化。没有进化或没有自然错误时，“随进化失准”问题记为本轮未被检验，而不是支持或否定。

## 流程二：冻结候选，进行一次验证器修订

对比三种验证器，评价对象是完全相同的冻结产物，而不是各自重新生成的答案：

| 条件 | 修订信息与调用链 | 输出 |
| --- | --- | --- |
| V0 | 原始 Coding Rubric，不修订 | 固定验证器 |
| V-feedback | 同一批 development 审计；计划 → 批判 → 修订，共 3 次调用 | 一个最终修订提案 |
| V-docs | 同一批 development 审计及研究资料；问题界定 → 资料综合 → 修订，共 3 次调用 | 一个最终修订提案 |

3 次调用是生成一个提案的阶段链，不是 3 次独立修订复现。两条链采用相同模型、匹配的每阶段输出预算，并报告实际输入、输出和总成本；资料阅读会增加输入，不能只凭调用数相同就声称总预算完全相等。链路结构也不同，因此两者差异首先属于整套修订流程之差，不能单独归因为“增加引用”或“研究资料内容”。

研究资料必须记录来源、检索时间、支持的规范或语义、适用条件及尚未确认的问题。资料用于提出验证缺口和反例，不直接认证新 Rubric 正确。不得包含 holdout 的参考代码或私有答案。公共资料可能已经存在于模型预训练中，本轮不宣称排除训练污染。

每臂只产生一个最终提案，全部报告，不凭 holdout 成绩挑选“最佳版本”。修订解析只检查结构、核心义务保留和修改幅度；格式通过不等于校准通过。原有请求正确性、约束保持、产物完整性义务不得被删除或降级。无效提案的失败必须保留，不能悄悄反复重试直到出现有利版本。

修订冻结后，用 V0、V-feedback、V-docs 对完全相同的 holdout 产物评分。匹配键为 `(id, skill_version, repeat, origin)`，配对双方的目标请求哈希和 oracle 必须一致；judge 请求哈希另存。缺失或不一致的证据不得悄悄删除。

本轮不将任何修订验证器正式晋级为默认 Gate，不将其反馈再接回 Skill 进化，不覆盖旧实验中的冻结代码或既有结论。后续协同闭环需另行冻结协议。

## 自然产物与受控产物

自然产物为模型真实执行结果，是主结果。受控材料用于故障诊断，必须独立报告：

- 原始待修复 starter：可能同时有请求错误和保护错误，不默认属于单一机制错误。
- 参考实现：正确产物控制，用于观察误拒绝；评委只看到普通候选代码，不知道它是参考实现。
- 一个预先定义的 preservation 缺陷变体：仅当它仍通过请求相关/公开检查且在保护检查上失败时，才标为“保护条件负例”；否则如实标为一般错误产物。

代码变体须在读取其 judge 结果前冻结，不能根据 V0 是否受骗继续修改直到成功。变体与原始任务共享 `cluster_id`。分别展示 starter / reference / preservation-defect 的明细；不得将它们混入自然错误率，也不能用受控比例代表实际部署风险。Judge 不接收 `origin`、控制类型或 oracle 身份标签。

## 评分和报告

主表分别报告自然/受控来源、Skill 版本、任务族和数据分割。至少包含任务数、簇数、响应数、硬验证通过数，以及以下量：

- TP：硬通过且 judge 通过；TN：硬失败且 judge 拒绝。
- FP：硬失败但 judge 通过；FN：硬通过但 judge 拒绝。
- 真通过/真失败上的 unknown，及 API、执行、schema 错误。
- 误放行率 `FP / 所有可观测硬失败`。
- 通过污染率 `FP / 所有具有可观测硬结果的 judge 通过`。
- 真通过接受率 `TP / 所有可观测硬通过`。
- 决断覆盖率及 schema 合法率，所有比率的显式分母。

unknown 是拒判，不是正确拒绝；schema/API 错误作为独立错误来源并以有效 unknown 计入有 oracle 的结果，不能通过删除失败行美化覆盖率。没有可用 oracle 的响应单独报告，不当作错误答案。分母为零时报告不可计算，不填零。

配对分析区分“错误的确定判断变正确”“正确判断变错误”“误放行转拒判”“拒判转正确”，防止把全部拒判误认为验证能力提升。报告逐题结果、具体新增/修复的漏检、误拒绝和成本。样本太小且有重复/变体依赖，不做确认性显著性、总体安全或因果主张。

## 预定反思与下一步

- 若自然产物接近全对：停止来源进化分支；验证器控制诊断仍可完成，但下一轮需另选有学习空间的真实任务族。
- 若 V0 存在明确漏检，修订在新的自然产物上纠错且未仅靠大幅拒判：支持扩大验证器校准样本，尚不证明协同进化有效。
- 若只在受控负例上改善：仅支持受控检测可行性，不宣称自然负迁移风险降低。
- 若 V-feedback 与 V-docs 无可辨别差异：不能宣称研究资料必要；后续需要更合适的新领域规范问题或成本匹配对照。
- 若修订增加误拒绝或 unknown：报告相应损失，不用单一误放行率宣布胜出。
- 若验证器改善但 Skill 分支未进化：两项结果分开表述；下一步是独立的新协议下的小闭环，而不是把本轮补写成协同进化成功。

只有在验证器修订的作用获得更充分独立证据后，才开展固定/动态验证器的端到端对照，并进一步扩展到跨领域任务流和冻结后的公开评测。

## 传输修订记录：v1 → v2

短请求预检在并发 1/4/8/12 下完成 51 次调用，均无终止错误或重试；正式长代码任务采用保守的 4 并发。但 v1 的首个 source 请求尚未展开并发，就连续三次收到服务端 HTTP 504，每次约 60 秒，共 186.14 秒。没有返回模型答案或 token 用量，也没有产生来源任务成绩。

因此 v2 仅将模型请求改为流式传输，继续收集最终内容、结束原因和用量，再使用原有解析与评分。任务、提示词、oracle、样本数、token 上限和决策规则不变。v1 的失败缓存、协议以及 9 个源码文件快照保留，所有快照与原协议哈希核对一致；v2 使用新的输出目录和源码快照。流式支持仍需真实探测，不能预先宣布已经解决服务端限制。

在正式使用新传输前，先执行流式健康检查；其调用不计入任务准确率。连接中断、缺失结束标识、截断或服务端错误不作为模型任务失败，也不允许用残缺答案进入修订。真实服务端已执行但未返回的调用可能计费，无法由客户端缺失用量推断其免费。

## 推理配置修订：v2 → v3

流式健康探测 5/5 成功。v2 首个完整任务请求以 HTTP 200 完成了传输，用时 173.37 秒，报告 2148 个输入、10000 个生成 token，但结束原因为 `length` 且正文为空；没有形成可评分的代码。该记录及源码 JSON 快照保留，不计为任务正确或错误。

GLM-5.3 官方说明支持 `reasoning_effort=low/high/max`、默认 max，不能使用旧型号的 thinking-disabled 设置。[型号文档](https://docs.z.ai/guides/llm/glm-5.3)

v3 保持模型、流式方式、任务、提示词、token 上限、样本数和评分规则不变，但对 solver、Skill optimizer、judge、两种修订链**统一显式请求 `reasoning_effort=low`**。这改变了推理计算条件，不仅是传输修复，因此设为新协议、新缓存目录，不能与其他档位混算。服务商是否实际执行该档位无法从客户端独立认证；记录所发送的参数与实际返回即可。前两次均没有模型答案或准确率，不存在根据已有成绩挑选推理档位。
