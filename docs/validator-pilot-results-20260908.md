# Coding 验证器先导：结果、失败诊断与下一步

日期：2026-09-08。模型：PJLAB `glm-5.3`。性质：小规模、描述性先导；不是 SkillOpt 官方结果复现，也不是完整协同进化或跨领域泛化实验。

## 结论先行

本轮已经写好并实际运行了“候选 Skill → 冻结产物 → 固定 Rubric 审计 → 开发集修订 → 留出审计”的有界实验框架。主流程完成，但**没有得到验证器修订有效、Skill 已协同进化或跨域安全泛化成功的证据**。

有用的发现是：

1. 来源集表面的 Skill 收益主要受到代码交付格式影响；对能提取且语法有效的 train/dev 代码，当前硬行为检查全部通过，尚未获得合适的语义学习空间。
2. V0 的确会误放行真实语义错误，也会误把确定的交付错误当作执行器故障；评分 JSON 失败还会让进化门长期无法比较候选。
3. 两条验证器修订臂分别因无效 JSON、官方资料获取失败而没有形成有效 Rubric，三臂有效性比较未完成。不能把工程失败解释为 DeepResearch 无效。
4. 已补充独立的格式敏感性分析、确定性公共检查诊断、安全代理检索和 JSON 模式回归。检索修复成功；JSON 模式的小样本配对测试没有显示稳定收益。

因此下一步应先解决产物/评分接口和语义学习空间，再做独立的验证器修订对照，最后才接入双向闭环。

## 1. 本轮写了什么

这是可选旁路，不替换默认 trainer；只复用 SkillOpt 的 Skill patch 应用器，不应称作完整 SkillOpt 优化算法。

| 部件 | 实现与作用 |
| --- | --- |
| PJLAB 传输 | `skillopt/validator_pilot/api.py`；只读 PJLAB 配置、流式响应、显式推理档位、有界重试、请求哈希、不可变缓存、耗时/HTTP 尝试/token 账本 |
| 公共任务与硬 oracle | `tasks.py`；9 个有版本来源的 Python 任务、公开与私有行为案例、参考实现/缺陷控制、受限子进程执行 |
| Coding Rubric | `rubrics.py`；V0、结构化判断、开发集修订、不可删除的核心义务、无效提案拒绝 |
| 官方资料修订 | `research.py`；研究问题、限定官方来源、资料快照、综合与 Rubric 修订接口；本轮实际仅完成计划阶段 |
| 实验与分析 | `experiment.py`、`analysis.py`；最多 3 个候选、版本冻结、自然/受控产物分开、配对审计、误放行/误拒绝/unknown 分开 |
| 后续独立诊断 | `validator_artifact_sensitivity.py`、`validator_document_transport.py` 及对应 CLI；不改主实验的冻结代码和成绩 |
| 入口 | `scripts/validator_pilot_preflight.py`、`scripts/validator_pilot.py`、`scripts/validator_json_mode_probe.py` |

数据流为：公开任务与起始代码 → Base/人工 Skill/候选 Skill 生成代码 → 公共执行证据供 V0 和候选生成使用 → 私有 oracle 独立审计 → 开发审计供两个修订臂使用 → 冻结 Rubric → 对同一批留出产物审计。

本轮没有实现或验证正式的 Cross-Domain Validation Gate、Commit/Restrict/Split 的完整决策器、多领域路由、验证器晋级，以及修订反馈重新驱动 Skill 的协同闭环。

## 2. 数据与实际运行条件

任务来自 [SkillEvolBench](https://github.com/AIoT-MLSys-Lab/SkillEvolBench)，固定提交 `9e3daa339987c3cfa624121e1be442593a53d43c`。来源与改编说明见 [任务 README](../configs/validator_pilot/tasks/README.md)。上游多文件项目被改编为单模块、权限受限的 Python 行为任务，私有行为案例为本地独立编写；不能将这里的分数标作官方 benchmark 成绩。

| 分割 | 任务族 | 任务 ID 后缀 | 实际用途 |
| --- | --- | --- | --- |
| train | E1-LS4，多文件缺陷/精度保护 | T1、T3、T6 | 来源产物、候选生成与影子门 |
| development | E1-LS5，合并冲突/语义整合 | T2、T4、T6 | 验证器审计与一次修订 |
| holdout | E1-LS3，安全重构 | T5、T6、T4 | 冻结后的描述性留出评价 |

每个分割只有 **1 个任务族/簇、3 个任务 ID**。每条件每任务 2 次生成，共 5 个内容条件、90 条自然产物；另在 dev/holdout 各放入 9 条受控产物，共 18 条。重复、变体和内容条件不是独立任务或训练种子。所有任务均为 Coding，不构成跨领域证据。

目标模型、V0 和 Skill patch 不接收参考实现、私有测试或私有期望输出。train 私有结果只用于预先规定的来源满分停止检查；dev 私有审计允许进入 Rubric 修订；holdout 不进入修订或候选选择。之后基于已看到的留出结果做出的诊断明确标为 post-hoc。

执行隔离使用 macOS `sandbox-exec`，阻断网络、仓库/私有目录访问、写入和额外进程；执行环境不继承凭据。另有 AST/标准库限制、CPU/墙钟限制和 RSS 轮询终止。RSS 检查不是硬内存分配上限；Linux 等未提供隔离后端的平台拒绝无隔离执行。有限硬测试不等于正确性证明。

传输和并发：

- 短请求预检并发 1/4/8/12，两波共 51 次，全部成功、无重试；不能据此宣称长任务能稳定保持 12 并发。
- 正式长请求采用 **4 并发、stream=true、reasoning_effort=low、temperature=0**，模型返回名均为 `glm-5.3`。服务商是否真正执行推理档位，客户端无法独立认证。
- v1 首个非流式任务连续三次 HTTP 504；v2 首个流式长任务返回空正文、`finish_reason=length`、10000 个生成 token。都未形成代码或准确率，失败缓存保留。
- v3 主实验约 31 分 51 秒：205 个逻辑调用、214 次 HTTP 尝试、9 次重试，无终止 API 错误。请求用时中位数约 11.17 秒，p95 约 74.45 秒，最长约 137.99 秒，包含重试等待；可见流式并非消除了所有传输中断。
- 主实验返回用量：输入 862,706、生成 163,721，合计 **1,026,427 tokens**。包括 solver、judge、Skill patch 和实际执行的修订阶段；不包括预检、早期失败尝试和后续 JSON 回归。未返回的服务端计算可能仍计费，用量不是账单。

模型档位设置依据 [GLM-5.3 官方说明](https://docs.z.ai/guides/llm/glm-5.3)。v1/v2/v3 变更时点、失败原因和声明边界保存在 [预先协议与修订记录](validator-pilot-protocol-20260908.md)。

全程用量的分项核对如下；未知不能填作零。

| 阶段 | 逻辑调用 / HTTP 尝试 | 已返回总 token |
| --- | ---: | ---: |
| 最初临时健康探测，仅对话工具记录、无归档请求哈希 | 1 / 1 | 232 |
| 首次预检，合法 JSON 围栏被旧解析器误拒绝 | 1 / 1 | 326 |
| 修正预检解析后的并发测试 | 51 / 51 | 21,393 |
| v1 非流式正式尝试 | 1 / 3 | 未知 |
| 流式健康探测 | 5 / 5 | 1,406 |
| v2 流式、默认推理档位正式尝试 | 1 / 1 | 12,148 |
| v3 主实验 | 205 / 214 | 1,026,427 |
| 后续 JSON 模式回归 | 7 / 7 | 31,466，另 1 次失败用量未知 |
| 合计 | 272 / 283 | 已知 1,093,398，另有未知用量 |

官方文档 HTTP 获取不属于模型调用。上述失败探测没有生成成绩，不混入主准确率。

## 3. Skill 内容条件的结果

下表是原协议的严格交付格式加硬验证通过数；每格分母均为 6。

| 内容条件 | train | dev | holdout |
| --- | ---: | ---: | ---: |
| No-Skill | 3/6 | 4/6 | 2/6 |
| 人工机制 Skill | 0/6 | 6/6 | 2/6 |
| Candidate 1 | 5/6 | 6/6 | 2/6 |
| Candidate 2 | 5/6 | 5/6 | 3/6 |
| Candidate 3 | 5/6 | 5/6 | 2/6 |

三个候选内容均成功产生，但**接受更新数为 0**。影子门要求 Current 和 Candidate 的全部判断均合法；人工 Current 的 2 条非法评分被缓存，使三轮都无法满足可比较条件。结果一直保留人工 Skill。因此这是从同一 Current 出发的三个候选提案，不是进化了三代。

Candidate 2 多通过一个 holdout 产物既不足以证明泛化，也不能作为挑选该候选的依据。这里不选择“最佳留出版本”。

### 为什么来源收益不能解释成机制学习

后续独立提取分析只接受无歧义的代码封装，不改代码逻辑或语法；原严格成绩不变。

| train 条件 | 原严格通过 | 仅提取封装后通过 |
| --- | ---: | ---: |
| No-Skill | 3/6 | 5/6 |
| 人工 Skill | 0/6 | 4/6 |
| 每个 Candidate | 5/6 | 5/6 |

30 条 train 产物中，提取后 24 条通过、2 条 Python 语法失败、4 条无法无歧义提取；没有观察到可执行产物的硬行为失败。dev 提取后 28/30 通过，其余 2 条无法提取，同样没有观察到可执行代码的行为失败。

这说明本轮来源/开发任务的语义难度和失误分布不够合适；部分收益是交付合规收益，而非已经学到 Constraint Preservation。不能对无法提取的答案推断其语义正确，也不能以这一条件化结果断言模型总体已经满分。

holdout 提取后为 13/30 通过；剩余 17 条分为 5 条无法提取、1 条语法错误、6 条受限运行/AST 契约违规、5 条行为或结构失败。不能将这些失败混称为相同的语义错误或 Skill 诱发负迁移。

## 4. 固定验证器到底漏了什么

留出自然产物 30 条，硬通过 11、硬失败 19：

| V0 结果 | 数量 |
| --- | ---: |
| 正确放行 TP | 10 |
| 正确拒绝 TN | 10 |
| 错误放行 FP | 2 |
| 错误拒绝 FN | 0 |
| 硬通过上的 unknown | 1 |
| 硬失败上的 unknown | 7 |

误放行率 2/19 = 10.53%；所有可观测放行中的污染率 2/12 = 16.67%；有效确定判断覆盖 22/30 = 73.33%。8 条 unknown 全部来自评分 schema 失败，不是模型输出的合法主动 abstain。不能将 unknown 算作正确拒绝，FN=0 也不代表所有正确答案都被接受。

两个误放行需要分开理解：

- **真实语义盲点**：`E1-LS3-T4 / noskill / repeat 0`。插件拿到活列表并原地修改后抛异常；`except: continue` 没有回滚数据。硬检查发现 `amount=1000, nested.x=999`，期望为 `amount=3, nested.x=1`。V0 却声称原数据被保留。它发生在 No-Skill，不能归因于 Skill 负迁移。
- **确定性交付错误误放行**：同一任务 `manual_seed / repeat 1` 的 JSON 交付失败，零测试执行。V0 把错误解释成 harness 问题而判通过。这一项不需要 DeepResearch 才能拦截。

同一 V0 在 `T4 / candidate_3 / repeat 1` 又正确指出活列表别名和回滚错误；在 `T6 / candidate_2 / repeat 0` 正确识别了本来允许 bool 输入、却新增 bool 排除规则的回归。因此应描述为上下文敏感的判断不一致，不能说它完全不理解保护机制，也不能据此证明随 Skill 进化发生漂移。

受控留出 9 条单独统计：3 个参考实现全部 TP；6 个错误产物中 4 个 TN、2 个 schema-error unknown、0 个 FP。总体标准差被改成样本标准差的 preservation mutant，原始评语正确指出 `n−1`，但评分 JSON 无效，因此正式结果仍是 unknown，不能记作成功检测。

## 5. 两个修订对照为什么没有有效结果

| 修订臂 | 实际执行 | 最终状态 |
| --- | --- | --- |
| 仅开发反馈 | gap analysis → critique → revision，3 次 API 调用完成 | 最终修订 JSON 无效；无有效 Rubric |
| 开发反馈 + 官方资料 | 研究计划 1 次 API 调用完成；随后 3 个资料 URL 全部被本地 DNS 安全检查拒绝 | 未做资料综合/最终修订；无有效 Rubric |

两臂原定最多各 3 阶段、匹配每阶段输出上限，并不意味着实际 token 成本相同。本轮实际阶段数都不同，不能比较等成本收益。

资料失败的直接原因是 Clash fake-IP DNS 返回 `198.18.*`，直接连接检索器按非公网地址拒绝。原运行没有静默退化成“无资料的资料臂”，也没有删除失败后继续抽样直到成功。最终留出只有 V0 的正式成绩；`results.json` 的 complete 表示流程走完，不代表三种验证器都有效。

## 6. 结果之后做的工程修复和额外实验

以下全部使用新文件/新输出目录，不覆盖原协议。它们是已观察结果后的诊断或工程回归，不是新的独立确认性实验。

### A. 严格公共检查前置：0 次模型调用

对冻结的同一批 V0 判断，加一个只读取产物的 JSON、Python 语法、AST 合规检查；确定不合格时由程序拒绝，不使用私有 oracle 作决策。

留出自然产物的 FP 从 2 变为 1，unknown 从 8 变为 2，确定判断覆盖从 22/30 变为 28/30，未增加 FN。具体是 1 个 FP→TN、6 个 unknown→TN；真实插件回滚语义漏检仍然存在。

这说明应由确定性检查处理已知硬契约，不能把所有判断交给语言模型。不过这些是同一批历史数据上的 post-hoc 重放；程序补出的决定不是 LLM schema 改善，也未实际验证在线成本节约。若后续改为宽松代码提取协议，Guard 必须按新产物契约设计，不能同时把可接受的封装判为不合格。

### B. JSON 输出模式：7 次新模型调用

只从 train 选择 4 个历史评分失败提示，固定提示做 fresh default / fresh `response_format={"type":"json_object"}` 配对、交替顺序，每臂最多一次、不重试。旧失败只作选择条件，不充当 fresh baseline。

完成 3 对双方传输成功的配对：default 合法 2/3，JSON 模式合法 1/3；其中双方合法 1 对、仅 default 合法 1 对、双方均非法 1 对。第 4 对首个 JSON 请求发生 HTTP 200 流中断，按预定停止规则结束，总计 7 次请求、6 次传输成功，返回用量 31,466 tokens。

本诊断没有证明 JSON 模式改善稳定性，也不能证明它普遍更差或推断 PJLAB 是否实际执行参数。合法 JSON 也不等于 Rubric schema 或语义正确。必须保留不完整配对和传输故障，不选取有利子集。

进一步检查：双方 JSON **语法**有效率其实均为 2/3；JSON 模式额外有一次因顶层键 `" "` 违反严格 schema 而失败，另一次输出以多余的 `{` 开头。三个无效完整响应均为正常 `stop`，不是输出上限截断；第七次传输失败则不能归类为模型生成了无效 JSON。三个完整提示对只涉及两个任务 ID，独立性比配对数量更低。

### C. 官方资料安全代理检索：0 次模型调用

新增显式固定的现有本地代理模式；只允许官方 HTTPS 域名、TLS 验证、逐跳检查、最多 3 页、45 秒异步请求截止、每页 2 MB/12,000 字符以及 HTML/文本哈希快照。不修改 Clash、DNS 或 API 连接路由，不放开私有地址直连；目标域名由受信本地代理解析，因此远端公网 IP 未被本地独立认证。

对原 V3 计划的 `re.match`、`str.isdigit`、`sqlite3` 三个官方 URL 实测 **3/3 获取成功**，各一次 HTTP GET、无重定向。这里只证明资料传输修复，不意味着原资料修订臂成功，也没有生成或晋级新的 Rubric。

## 7. 下一步的明确顺序

**先完成接口可靠性和任务选择，不立刻堆完整协同进化系统。**

1. **冻结新交付/评分协议。** Coding 产物采用明确的代码或 patch 通道，避免大段 Python 嵌入 JSON 的转义负担；评分缩小 schema、把决定和证据分离，使用有界、可审计的格式修复/重判。加入公共执行的硬失败前置检查。unknown 不伪装成通过，也不应让同一条缓存错误永久阻断进化；设置重判预算或保守上下界比较，并明确 fallback。
2. **重新寻找真实语义学习空间。** 在新的来源/开发项目上跑少量 No-Skill 预检，分开记录交付错误、权限违规、运行失败和行为失败。选任务的规则和用量要记录，不能按候选胜负选题。优先保留真实多文件 patch、依赖与回归测试；需要容器后端才能放宽当前单模块沙箱。目标是发现可以由机制 Skill 改善的自然行为错误，而非挑一个更容易产生格式差异的样本。
3. **重做独立验证器修订实验。** 在同一冻结代码产物上对比 V0、仅反馈修订、反馈+官方资料修订。开发集包含真实语义错误与受控反例但分别统计；Rubric 经独立校准、核心义务保留且不靠全面拒判获利后才能晋级。匹配调用和实际 token 成本的差异应分别报告。新确认性留出不能复用本次已经查看过的 LS3 结果。
4. **通过后才接协同闭环。** 设置 Skill 版本和 Validator 版本两个独立晋级门：Skill 用当前冻结 validator 提案/验证；validator 用新积累的开发审计提出修订，再过独立校准门。先比较固定/动态 validator 的小规模任务流，记录真实接受更新、旧任务保留、unknown 和成本，而不是只看累计分数。
5. **最后进入跨领域。** 以机制组织 different-domain/same-mechanism、same-domain/different-mechanism 和 unrelated 三类验证；在冻结 Skill/validator/router 后评测新公开 benchmark。DeepResearch 的角色是提出规范依据、验证缺口和反例，不是替代独立行为证据的最终裁判。

目前没有证据要求更换模型，后续仍可先使用 PJLAB `glm-5.3`。单一模型兼任 solver/judge 的相关偏差需要作为限制保留；如果之后做外部评委或跨模型验证，再单独确认模型和预算。
