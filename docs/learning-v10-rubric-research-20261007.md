# 学习v10：主方法（Coding Rubric → probe → Research）接入五域持续协议（2026-10-07）

状态：实现＋Codex审查中；付费启动与结果见文末“进展”。本文是设计/实施记录；数字以`docs/results-and-lessons.md`账本和导出JSON为准。

## 1. 为什么要接

10/6–10/7的G系列（`docs/learning-v8-generalization-gate-20261006.md`）跑的全是两条**基线**优化器（仓库原生SkillOpt文本梯度循环、官方GEPA）加一层方法无关的协议升级（val选择、噪声校准门控、**benchmark标签**失败反馈、迁移前言）。README定义的主线——“通过Coding Rubric与有界DeepResearch协同改进Skill”，代码在`skillopt/skill_validation/`（`natural_policy`、`probe_review`、`probe_fact_research`、`task_probes`、`closed_loop`）——此前只在9月的小规模协同进化系列（v3–v18）和自然数据pilot上运行，从未接到`fivebench-split-v2`和G阶段工具上。用户10/7上午确认：主方法取**Rubric→probe→Research**路线，并要求接好、Codex审查、启动评测。

## 2. 设计：学习v10（`continual-learning-v10`，方法`rubric_research`）

v10 = v9协议（两遍族级符号检验门、解析器v2、一次JSON格式重试、8192反思上限、8并发solver）**只换反馈来源**：失败的train行不再附benchmark标签（期望答案/脱敏隐藏测试证据），而是附一个**无标签验证器**的报告。Skill更新器仍是仓库原生SkillOpt优化器（analyst→merge→ranking），因此与v8/v9基线的比较隔离的是反馈来源这一个轴：标量（F/v7）／验证器（v10）／oracle标签（v8/v9）。

每个学习步，在父Skill已执行的train行上（`skillopt/continual_learning/verifier.py`）：

| 步骤 | 内容 | 模型调用（角色`verifier`） |
|---|---|---|
| 1 Rubric提案 | 有界开发视图（≤16行：公开题面、生成产物≤3000字符、宿主开发审计pass/fail——标注为宿主信息、不算Research发现）→ plan（缺口问题≤3，Research臂可从**冻结的16页Python 3.11官方文档**选≤3页）→ 取文档 → synthesis：七字段可复用条件化验证策略（mechanism/obligation/applicability/exceptions/evidence_required/check_generation/uncertainty，obligation固定为requested_behavior），引用须是可用文档的20–500字符逐字摘录（v3起按**空白折叠**匹配：抽取的页面文本保留硬换行而模型会改写成空格，措辞仍须逐字；改述照旧拒绝）。synthesis若未通过严格校验（引文不逐字、字段超500字符、JSON残缺），带着原提案与确切错误**只重试一次**（`synthesis_repair`），再失败则策略保持上一步、记录失败原因 | 2–3 |
| 2 probe实例化 | BCB：每题≤2个公开probe——入口函数的JSON调用＋期望JSON值（`expected`），同一实现两次调用的相等关系（`equal_relation`），或v4起的**文档化异常**（`raises`：一次调用、输入满足题面写明的出错条件、`expected`为该异常的内置类名且contract_quote须写明它——主线pilot `skill_validation/checks.py`的`expected_exception`的移植；把异常编码成期望值的`expected` probe被拒）；contract_quote必须是题面逐字子串；期望值只能从契约推出；返回或接收不可JSON表达对象（文件、图、DataFrame、随机、网络）的函数不出expected/relation类probe，但可出由JSON参数触发文档化异常的`raises` probe。QA/KOR：裁判调用在**不知参考答案**的前提下对策略义务（答案形式、范围、规则步骤的可见应用、输出格式）给出pass/fail/unknown | 每行1 |
| 3 执行前审阅 | BCB：每个probe keep/drop＋可选“语言事实问题”；有问题且Research臂→选≤2页文档→按文档决定keep并可**带引用**修正期望值（仅expected类probe）。未审阅的probe绝不执行 | 有probe的行1，+Research≤2 |
| 4 执行 | BCB：把kept probe生成为官方harness格式的`TestCases`，用冻结评测同一条`backends._native`路径在**同一pinned容器**里跑（`untrusted_check`，与隐藏测试同隔离/同超时）；按`test_probe_i`回溯逐probe判pass/fail/error/unknown：只有末行**以本组probe的随机数标记开头**的harness自身断言（`verifier probe [<nonce>]:`，nonce由kept probe的六个字段派生，候选程序生成时不可能知道）才算fail，以同一标记开头的序列化错误（结果含图、DataFrame等不可比较对象）是unknown（不计分母，按宿主状态另记覆盖），其余一切（候选自己抛的异常，无论文本如何）是诊断性error；`raises`：抛出文档化异常（或其子类）=pass、正常返回=fail、抛别的异常=error；容器清理未确认→停（与v6硬化规则一致） | 0（容器） |
| 5 校准 | 宿主侧（`host_only/verifier/<step>/calibration.json`）：在宿主判pass的产物上失败的probe是误拒，整行丢弃；**宿主判pass且执行了probe的对照行≥5**（否则误拒率无定义、不授权）、检出数≥1、丢弃前误拒率≤0.25才**授权**本步报告与策略文本进入analyst；否则本步analyst得到与v9相同的提示（无报告、无策略），Skill循环按共同的标量证据继续，记录`authorized=false` | 0 |

analyst（仅在授权步）看到的是失败行的`Feedback.verifier`文本（`render_feedback`：机制一句、每个probe的调用/期望/结果/契约引文/断言信息、≤2条文档引文，≤1800字符）加系统提示末尾的`VERIFIER_PREAMBLE`（如何使用报告、禁止把probe输入/期望值/实体写进Skill、当前策略）。**绑定**：trace里的verifier文本必须等于**重新读取的**同一执行证据密封报告`verifier/<step>/reports/<evidence>.json`，且报告绑定本manifest、本步、本步授权策略哈希并`authorized=true`；每行记录在生成提示前先与保存的评测记录核对任务哈希/输出/分数（未知行过滤后仍成对）；提案identity含授权标志、策略哈希与全部报告哈希；每次容器执行先写intent再写receipt（清理未确认→intent悬空→阶段不能完成，`_evaluations_closed`与`require_safe_handoff`都检查）；验证器调用`ok=false`→阶段Pending（截断/畸形回复才是单元级结果）；策略/行/摘要/报告的重放都核对manifest、步、父策略、视图哈希与行记录哈希；验证器调用按**已提交intent**而非回执计数封顶（并发安全）；Research对期望值的修正只在整份回复合法时整体生效。`verifier/**`与`host_only/verifier/**`下的**全部文件**（含取回的文档字节）进入artifacts清单与G工具的证据盘点；`validator_pilot/research.py`纳入源码身份。

**不进入任何模型提示**：隐藏测试、参考答案、宿主审计原因。宿主审计的pass/fail只作为开发视图里的标注和校准依据（主线“独立校准接口”的对应物）。v10下`_record_exposed_labels`不记录任何标签（analyst未见），泄漏检查因此为空操作。

**Rubric随链共同进化**：提案器每步从上一步策略继续（视图里附上一步的校准结论）；analyst与下一阶段只拿**最近一次通过校准的策略**——阶段结果记录`verifier_policy`（按域映射），`learned.json`记其哈希；`--parent g:<dir>`从已完成的`rubric_research`阶段读入映射并绑定哈希，下一阶段取本域条目（无则冻结默认策略）；跨域阶段各自独立演化。

**预算**：`BUDGET_V10 = BUDGET_V9 + {max_verifier_calls: 2000, verifier_max_tokens: 4096}`，账本新角色`verifier`按已提交intent单独封顶；用量仍按真实回执。每步上界：策略2（v3起含一次修复调用则3）＋每个已执行train行（BCB/QA 128、KOR 90）probe/裁判1＋有probe的行审阅1＋有事实问题的行Research≤2 = 3＋128×5 = 643，三步上界1,929；v5每次调用至多再加一次格式重试，上界变为策略≤6（plan、synthesis、修复各至多2）＋每行≤8 = 6＋128×8 = 1,030/步、三步3,090，理论上超过2,000上限——只有绝大多数调用都需重试时才会触顶（实测不可解析率≈0.5%），触顶仍是安全停止；现实约150/步（链d实测：step 0共150次验证器调用，含plan、synthesis、128次probe、14次审阅、22次执行）。封顶是安全停止而非预期成本；触顶→BudgetExhausted→阶段Pending（已接受前缀在全部评测与容器执行闭合时按v8规则保留）。传输失败同理：验证器调用`ok=false`→Pending，同样适用已接受前缀例外。

**域覆盖**：Research（文档源）只对BCB定义（QA/KOR的plan不得带URL，相当于主线的`adaptive_no_research`臂）；QA/KOR用裁判式probe。Sheet/ALF不在API-only工具范围内（同G）。

## 3. 与主线pilot的对应与简化

- 对应：七字段策略与两调用提案（`natural_policy.propose_policy`）、probe格式与实例化提示（`probe_messages`）、执行前审阅（`probe_review`）、按缺口的有界事实Research（`probe_fact_research`：官方页≤2、模型只选内容/引用）、“假设≠任务真值、引用证明出处而非真理、允许no_update”的原则。
- 简化（Codex审查特别指出，读者不应误以为是完整主线）：**校准在用于策略开发的同一批train产物上进行**，没有独立校准分区，也没有跨配对Skill条件的共用probe——这是“反馈来源”实验的简化实现，不是主线那套独立校准的验证器准入流水线；**Research可以直接修正probe的期望值**（pilot只重审原检查、不改期望值），修正须带文档引用（且不得把期望值改成异常编码）；`raises`按isinstance判定（子类算通过，与benchmark的assertRaises一致；pilot比较异常名全等），抛出别的异常仍是诊断性error（pilot判fail）——沿用v2起“只有harness断言计分”的规则；验证器不参与test推理（test是冻结solver＋Skill文本，与基线相同）；BCB入口`task_func`由宿主固定，不支持`input_state`类probe；判定/选择仍由H在val上完成（与所有方法相同）。train规模与G一致：BCB 128题（不是F开发集的65题）、QA 128题、KOR 90题。**论文须逐条写明这些简化（用户10/7确认）**，并写明同批产物校准的直接后果：宿主fail行上验证器自己的期望值写错也会计为“检出”（链e step 2即为一例），校准只能在宿主pass对照上发现误拒；抛错调用只作诊断、不计分；引文证明出处而非真值。
- 预期（诚实写在前面）：v8的BCB阶段在analyst看到脱敏隐藏测试证据时三轮候选仍全被拒，v10的probe信号弱于隐藏测试，故BCB上大概率仍无更新；QA的增益是答案形式，裁判式probe有机会与oracle标签持平；KOR胜负是单字符执行滑移，任何反馈都难以改变。v10的价值主张是**无标签**而非更强——若与oracle条件持平就是正面结果。
